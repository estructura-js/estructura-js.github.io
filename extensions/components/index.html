Components

Descripción

Proporciona un ecosistema modular orientado al desacoplamiento de interfaces mediante la inyección asíncrona y coordinada de recursos HTML, CSS y JS. El sistema gestiona automáticamente el ciclo de vida de los componentes, la resolución de dependencias declarativas en el DOM, la mitigación de colisiones de IDs y flujos de degradación fluida ante fallos de carga o de red.

Librería: estructura.components.js

Dependencia obligatoria: estructura.http.js (HTTP, documentación). El objeto global _http debe estar disponible en el entorno antes de inicializar cualquier componente; de lo contrario, el proceso se interrumpirá emitiendo una excepción en consola.

Documentación

1. Inicialización y Configuración de Componentes

El controlador global _components inicializa y orquesta componentes autónomos y coordinadores jerárquicos definidos en el documento.


Configuración global del entorno:

_components({
	origin: './src/components/',	// Ruta raíz predeterminada para recursos estáticos
	timeout: 10000,		// Límite de tiempo global de peticiones (10s)
	autoScan: true		// Iniciar el escaneo y montaje del DOM automáticamente
});

Inicialización manual sobre el DOM:

La invocación directa de la función constructora _components(element, config) devuelve la instancia del componente creado o, si solo se ha declarado un contenedor organizativo, el coordinador correspondiente. Esto facilita la captura y asignación de la referencia en una sola instrucción.

var nodo = document.querySelector('#contenedor-dinamico');

var instancia = _components(nodo, {
	component: 'ficha-usuario',
	id: 'tarjeta_activa',
	componentOrder: 'css,html,js',
	timeout: 15000
});

2. Declaración de Atributos en HTML

La declaración de componentes y coordinadores se realiza principalmente de forma semántica en el marcado HTML a través de atributos específicos.


Atributos para Componentes Individuales (data-e-component-*)

  • data-e-component (String): El nombre lógico de la carpeta o subdirectorio del componente.

  • data-e-component-id (String): Identificador único de instancia dentro del registro. Si colisiona con un ID existente, el motor lo resolverá agregando sufijos incrementales (ej: mi-id_1). Nota: Se generará una advertencia en la consola y los mensajes o eventos enviados explícitamente al ID original no serán redirigidos a las nuevas instancias renombradas secuencialmente.

  • data-e-component-src (String): Ruta o URL directa que anula el origen (origin) global.

  • data-e-component-order (String): Orden de descarga y aplicación de los recursos estáticos (por defecto: "css,html,js").

  • data-e-component-required (String): Relación de identificadores de componentes cuya carga exitosa es requisito previo para iniciar la inicialización de este componente. Admite múltiples valores delimitados por comas, espacios o saltos de línea (se procesa mediante la expresión regular /[\s,]+/).

  • data-e-component-fallback (String): Nombre lógico del componente de contingencia alternativo que se cargará si falla el flujo principal.

  • data-e-component-fallback-src (String): Ruta de origen opcional para el componente de contingencia.

  • data-e-component-fallback-order (String): Estructura del orden de carga de recursos del componente de contingencia.

  • data-e-component-timeout (Number): Límite de tiempo de carga específico para este componente.

Atributos para Coordinadores (data-e-components-*)

  • data-e-components (Boolean/String): Convierte el elemento en un contenedor organizativo que sincroniza y asocia a los hijos con atributos data-e-component.

  • data-e-components-origin (String): Base de direccionamiento unificada aplicable a todos los componentes descendientes directos.

  • data-e-components-order (String): Cadena que describe el ordenamiento de carga secuencial y paralelo de los subcomponentes.

  • data-e-components-fallback-origin (String): Base de direccionamiento de contingencia unificada aplicable a todos los componentes alternativos descendientes directos que requieran fallback.

  • data-e-components-fallback-order (String): Orden de carga de recursos alternativos aplicable de manera predeterminada a todos los subcomponentes en estado de degradación.

Nota sobre la nomenclatura de rutas de contingencia (Fallback): El motor implementa una búsqueda ascendente en el árbol DOM. Si un componente individual no define de forma explícita su origen o secuencia de contingencia con los atributos de componente individual (data-e-component-fallback-src o data-e-component-fallback-order), el sistema buscará recursivamente hacia arriba en los nodos padres los atributos correspondientes del coordinador (data-e-components-fallback-origin o data-e-components-fallback-order).


Comportamiento de Declaraciones Híbridas: Si un único elemento DOM se declara simultáneamente como componente (data-e-component) y como coordinador (data-e-components), el motor ejecutará una inicialización en cascada: primero se montará el componente individual y, tras alcanzar el estado listo ("ready"), se iniciará de forma automática el coordinador asociado para procesar a sus descendientes.


3. Orquestación e hilos de carga

Los coordinadores permiten definir secuencias híbridas complejas para optimizar el rendimiento y la experiencia del usuario:

  • El operador coma (,) indica una secuencia obligatoria de pasos en cascada (esperar la preparación del bloque anterior para continuar).
  • El operador suma (+) indica la paralelización de llamadas de red e inyección en el DOM dentro del mismo bloque temporal.

Ejemplo de orquestación mixta:

<!-- Descarga 'estilos-base' y 'lateral' simultáneamente. Una vez listos ambos, se descarga y monta 'panel-principal' -->
<section data-e-components="mi_coordinador" data-e-components-order="estilos-base+lateral, panel-principal">
	<div data-e-component="estilos-base"></div>
	<aside data-e-component="lateral" data-e-component-id="lateral"></aside>
	<div data-e-component="panel-principal" data-e-component-required="lateral"></div>
</section>

4. APIs de Instancia y Eventos de Ciclo de Vida

Las instancias generadas por el motor proveen propiedades de consulta y métodos de suscripción a eventos internos.


Interfaz de Instancia:

  • id (String): El identificador único final asignado a la instancia.

  • element (HTMLElement): Referencia al nodo físico en el DOM.

  • options (Object): Configuración activa resuelta para la instancia.

  • status(): Retorna el estado actual de la instancia. Los estados posibles son:
    • "pending": Creada, esperando asignación del ciclo o resolución de dependencias requeridas.

    • "loading": Realizando peticiones de red y aplicando recursos principales.

    • "loading-fallback": Error detectado en la vía principal, montando recurso alternativo.

    • "ready": Proceso de carga y adición de recursos completados.

    • "failed": Error irrecuperable en el ciclo de inicialización o en sus dependencias.

  • _destroy(isReset): Invoca la desconexión de observadores, la remoción de oyentes de eventos y la baja del registro de la instancia. El parámetro booleano opcional isReset indica si la llamada procede de un restablecimiento de caché global, evitando la advertencia de descarte de nodos activos aún presentes en el árbol de renderizado.

Suscripción a Eventos

El objeto de instancia incorpora un emisor de eventos interno que permite añadir oyentes mediante los métodos on(), once() y off():

var inst = _components.get('panel-principal');

if (inst) {
	// Suscripción de ciclo completado
	inst.on('ready', function() {
		console.log('El componente ya tiene aplicados sus estilos, html y scripts.');
	});

	// Suscripción de errores de carga del componente
	// Captura fallos de red, timeouts de descarga y excepciones producidas en el JS inyectado
	inst.on('error', function(err) {
		console.error('Incapacidad para procesar el componente:', err.message);
	});
}

Mecanismo de Cola de Eventos:

Para evitar la pérdida de mensajes durante la fase de carga asíncrona, el motor incluye una cola de retención con un tamaño máximo de 50 mensajes. Los eventos enviados con _components.emit('id_destino', 'evento', data) se almacenarán temporalmente si el componente destino no está listo (estado diferente de "ready"), liberándose de forma secuencial una vez inicializado.

Nota sobre estados fallidos: Si el componente de destino se encuentra en estado "failed", cualquier envío de eventos mediante _components.emit() será descartado inmediatamente y se emitirá una advertencia en la consola, impidiendo que el mensaje se agregue a la cola de retención.


5. Métodos de Control Global

La biblioteca expone una serie de utilidades y hooks a nivel global en el objeto _components:


  • _components.get(id): Recupera la instancia activa de un componente a través de su ID unívoco.

  • _components.emit(targetId, event, data): Distribuye eventos globales hacia componentes específicos de forma segura.

  • _components.order(name, value?): Permite registrar o consultar alias reutilizables para flujos de carga preestablecidos.

  • _components.scan(root?): Ejecuta una inspección sobre el subárbol DOM especificado (o sobre todo el cuerpo del documento) inicializando elementos con atributos de componente.

  • _components.autoScan(): Asegura la inicialización automática del árbol del documento una vez se complete la carga del DOM.

  • _components.resetCache(): Libera memoria. Destruye instancias activas de forma ordenada, desconecta observadores globales y purga la caché de recursos y órdenes cargados.

Mecanismo Observador de Estados Globales:

Es posible adjuntar funciones observadoras globales para trazar el flujo interno de los componentes del sistema (ideal para tareas de depuración o construcción de indicadores de carga externos):

// Registrar monitorización de estados
function miObservador(id, estado) {
	console.log('[Monitor de Ciclo de Vida] Componente "' + id + '" cambió a estado: ' + estado);
}

_components._registerStateObserver(miObservador);

// Si se desea remover posteriormente:
// _components._unregisterStateObserver(miObservador);

6. Arquitectura y Características Técnicas

Caché unificada y deduplicación de red: Consolida peticiones en cola. Si múltiples elementos solicitan el mismo archivo estático (CSS, JS) en el mismo periodo, se realiza un único viaje de red, optimizando el ancho de banda. Tanto los recursos cargados como las estructuras de ordenamiento parseadas se almacenan en una caché de memoria limitada a 100 registros máximos por tipo, aplicando un mecanismo de desalojo estructurado FIFO (First-In, First-Out) al exceder dicho límite.


Recuperación y Degradación Fluida (Fallback): El motor transfiere de forma transparente las colas de eventos pendientes y los oyentes personalizados asignados a la nueva instancia de contingencia (fallback) en caso de fallos críticos del componente original. Los oyentes para eventos nativos de ciclo de vida (ready y error) están excluidos de esta transferencia automática para evitar activaciones duplicadas redundantes, siendo gestionados directamente por el framework.


Ejecución Segura y Mitigación de CSP: Los archivos javascript inyectados dinámicamente son aislados dentro de bloques de control de excepciones (try/catch) mediante un wrapper de ejecución. Las excepciones de ejecución producidas dentro del código inyectado se interceptan de forma controlada y se notifican al flujo de la instancia correspondiente mediante su evento de error. Si se imponen restricciones de Content Security Policy (CSP) en el uso de Blob URLs, el motor ejecuta un mecanismo de contingencia directa evaluando el texto en línea de forma segura.


Recolección de basura automatizada (Garbage Collection): Integra un sistema centralizado basado en MutationObserver. Monitorea cambios estructurales en el cuerpo del documento y detecta desconexiones del DOM (usando validaciones de conexión nativas isConnected) para invocar de forma automática la destrucción interna de instancias, liberando escuchas y memoria sin requerir intervención manual.


7. Consideraciones Técnicas y Optimización

Ámbito de aplicación de estilos (Shadow DOM): El motor añade los elementos de estilo (<style>) directamente en document.head. En caso de integrar estos recursos dentro de arquitecturas basadas en Shadow DOM, es recomendable tomar en cuenta que las reglas CSS globales inyectadas no penetran la barrera de encapsulación por defecto, requiriendo estrategias de herencia o importación alternativas.


Entornos de Renderizado del Lado del Servidor (SSR): Las referencias globales a variables de entorno del navegador (tales como window o document) se encuentran aisladas mediante verificaciones condicionales básicas en los puntos críticos de inicialización de la biblioteca. Sin embargo, para flujos de ejecución híbridos o arquitecturas de pre-renderizado (SSR), se sugiere programar la ejecución del escaneo o inicialización manual exclusivamente en ganchos del ciclo de vida del lado del cliente (client-side) para evitar excepciones debidas a la ausencia de APIs del DOM.
