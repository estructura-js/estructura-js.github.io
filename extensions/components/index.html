Components

Description

Loads interface components made of HTML, CSS, and JS files, asynchronously and in a coordinated way. The library manages each component’s lifecycle, the load order and dependencies declared in the DOM, ID collisions, and fallback components for load or network failures.

Library: estructura.components.js

Compatibility: ES5/ES6+

Status: RC3

License: AGPL v3

Required dependency: estructura.http.js (HTTP, documentation). The global _http object must be available before Components is loaded; if it is not, the library throws an exception when it loads.

Import:
<!-- DEPENDENCY: Estructura / HTTP -->
<script src="https://estructura.okzgn.com/extensions/http/estructura.http.js"></script>

<!-- EXTENSION: Estructura / Components -->
<script src="https://estructura.okzgn.com/extensions/components/estructura.components.js"></script>

Documentation

Quick start

Create one folder per component with the .css, .html, and .js files, set the base folder with origin, and initialize the element:

<!-- Loads ./components/greeting/.css, ./components/greeting/.html, and ./components/greeting/.js -->
<div id="greeting" data-e-component="greeting">Loading…</div>

<script>
_components({ origin: './components/' });
_components(document.getElementById('greeting'));
</script>

1. Initialization and configuration

The library exposes the _components function. Its return value depends on the argument:

  • Global configuration: With a plain object, it updates the global options and returns an object with the .config() method, which returns the active options.
  • Element initialization: With a DOM node, it starts the component or coordinator declared on it and returns an object with the .ref() method, which returns its instance (see section 4).

Global configuration

var activeConfig = _components({
    // Base folder where components are looked up
    origin: './src/components/',

    // Maximum time for each request, in milliseconds (10 s)
    timeout: 10000,

    // If true, runs _components.autoScan() (false by default)
    autoScan: false,

    // File name of each resource inside the component’s folder
    files: {
        css: '.css',
        html: '.html',
        js: '.js'
    },

    // Optional allowlist of external origins (null = no restriction)
    allowedOrigins: ['https://cdn.example.com']
}).config();

files property (Object): Defines the file name of each resource type (css, html, js). The value is appended as is to the path of the component’s folder, so by default the files requested are literally named .css, .html, and .js. For example, with origin: './components-origin/' and data-e-component="test", the library requests ./components-origin/test/.css, ./components-origin/test/.html, and ./components-origin/test/.js. With files: { css: 'styles.css', html: 'view.html', js: 'script.js' }, it would request ./components-origin/test/styles.css, etc. If a type is missing from files, '.' + type is used. It can also be set per instance in the second argument of _components(element, options); that instance’s fallback component uses the same files (and also the timeout and origin passed as options).

allowedOrigins property (Array|null): Optional allowlist of origins from which resources may be downloaded (e.g., 'https://cdn.example.com'). It is null by default, and no restriction is applied. Each URL is resolved to an absolute URL against document.baseURI before the request, and the page’s own origin (location.origin) is always allowed. Listed origins are normalized the same way as the target URL (lowercase, no trailing slash, and no default port: 'https://cdn.example.com:443/' is equivalent to 'https://cdn.example.com'); the '*' wildcard allows any origin, and an empty array ([]) limits loads to the same origin. A rejected request is not cached and is treated as a load failure of that resource (see section 2): a rejected CSS or HTML file only produces a warning, and a rejected JS file makes the component fail and triggers its fallback, if it has one.

Security note: The origin attributes (data-e-components-origin, data-e-component-src, and their fallback variants) determine where JavaScript is downloaded and executed from. If the DOM can contain user-provided HTML (comments, profiles, editable content), an attacker could insert these attributes and make the page load and run third-party scripts. In production, setting allowedOrigins to the trusted origins is recommended (or [] if all components are served from the same origin).

// Only the same origin and your own CDN are allowed
_components({ allowedOrigins: ['https://cdn.example.com'] });

Manual initialization with options

Options in the second argument take precedence over the element’s attributes. They are equivalent to the attributes in section 2: component, id, origin (base folder, like data-e-components-origin), src, componentOrder, required, fallback, fallbackSrc, fallbackOrder, timeout, and files; for a coordinator, components and order. Unlike _components.scan(), each call creates a new instance even if the element already has one: the previous one leaves the registry and the new one gets a renamed ID (e.g., greeting_1).

var container = document.querySelector('#user_card');

// Mounts the component and gets its instance
var component = _components(container, {
	component: 'customer-profile',
	id: 'active_card'
}).ref();

2. DOM attributes

Components and their relationships are declared in the HTML with the following attributes.

Component attributes (data-e-component-*)

  • data-e-component (String): The component name, which is also the name of its folder: the files are requested from origin + name + '/'. If data-e-component-id is not given, it is also its ID.
  • data-e-component-id (String): The instance ID in the registry. If the ID is already registered, the library renames it sequentially (e.g., id_1) and logs a warning to the console; this also happens between children of different coordinators. A coordinator reuses an existing instance only if it belongs to the same element. Note: messages sent to the original ID do not reach renamed instances.
  • data-e-component-src (String): The full path of the component’s folder for this instance (e.g., https://cdn.example.com/ui/button/). It replaces origin + name: the component name is not appended. If it does not end in /, one is added.
  • data-e-component-order (String): Which resources are loaded and in what order (default: "css,html,js"). Supports + for parallel loads (e.g., "css+html,js") and aliases registered with _components.order(). A resource that is not listed is not loaded.
  • data-e-component-required (String): IDs of the components that must be in the "ready" state before this one is loaded, separated by commas or spaces. The dependencies must exist when this component starts loading (for example, in an earlier step of the order): if an ID does not match any registered instance or any name in the coordinator’s order, the component fails. If one of those dependencies fails, this component fails too, without trying its fallback. Inside a coordinator, a component with this attribute (with IDs or with "true") is critical: if it fails, the coordinator stops the orchestration. With "false" or without the attribute, its failure does not stop the following steps.
  • data-e-component-fallback (String): Name of the fallback component that is loaded, with the same ID, if the main load fails. It is looked up like any other component (origin + name + '/'), unless a fallback path is given.
  • data-e-component-fallback-src (String): The full path of the fallback component’s folder, like data-e-component-src.
  • data-e-component-fallback-order (String): Load order of the fallback component’s resources (default: "css,html,js").
  • data-e-component-timeout (Number): Maximum time for each request of this instance, in milliseconds.

If loading the CSS or the HTML fails, the library logs a warning to the console and continues. If the JS fails (network error, timeout, or an exception while running it), the component fails and its fallback is loaded, if it has one. The CSS and JS of each URL are applied only once per page (until _components.resetCache()): if several instances use the same component, the HTML is inserted into each one, but the JS runs only for the first one.

Coordinator attributes (data-e-components-*)

  • data-e-components (String): Marks the node as the coordinator of the components it contains. Its value is the ID under which the coordinator is registered, which can be used with _components.get(), in data-e-component-required, or in the state observer. A coordinator initialized with _components(element) or _components.scan() needs a non-empty value; coordinators nested inside a loaded component can omit it, and in that case they are not registered.
  • data-e-components-origin (String): Base folder of the components: each one is requested from origin + name + '/'. It is inherited: each component uses the nearest data-e-components-origin (on the element itself or on an ancestor) and, if there is none, the global origin option. To set the exact folder of a single component, use data-e-component-src.
  • data-e-components-order (String): Load order of the child components, identified by their data-e-component value (see section 3). Supports aliases registered with _components.order(). Only the children listed in it are loaded (without this attribute, none are). Each name loads the first child with that data-e-component: if several children share a name, the others are not loaded.
  • data-e-components-fallback-origin (String): Fallback path inherited by components that do not declare data-e-component-fallback-src; the nearest one is used (on the element itself or on an ancestor). It works like data-e-components-origin: it is a base folder to which the fallback component’s name is appended (e.g., with ./backup/ and data-e-component-fallback="notice", ./backup/notice/ is loaded). In contrast, data-e-component-fallback-src is the full folder of the fallback component.
  • data-e-components-fallback-order (String): Fallback load order inherited by components that do not declare data-e-component-fallback-order; the nearest one is used (on the element itself or on an ancestor).

Inheritance of fallback attributes

When a component switches to its fallback, for each of data-e-component-fallback-src and data-e-component-fallback-order that it does not declare, the library searches up the DOM tree for the nearest data-e-components-fallback-origin or data-e-components-fallback-order, respectively. The fallback is attempted only once: if it also fails, the component moves to "failed".

Component and coordinator on the same node

If a node has both data-e-component and data-e-components, the component is loaded first and, when it reaches the "ready" state, the coordinator starts on the loaded content, even when the node is a child of another coordinator. The two instances coexist: _components.get() finds the component by its ID and the coordinator by the value of data-e-components.

3. Orchestration

A coordinator’s data-e-components-order attribute defines the load order of its child components with two operators:

  • Comma (,): Successive steps: a step starts when all the components of the previous step have finished.
  • Plus (+): Components in the same step, which are loaded in parallel.

Orchestration example

The names in the order refer to each child’s data-e-component value, not to its ID: side-menu is found by its name even though its ID is left_menu.

<!-- Loads 'base-layout' and 'side-menu' in parallel. When both finish, loads 'control-panel'.
     It is started with _components.scan() or with _components(element) on the div. -->
<div data-e-components="my_dashboard" data-e-components-order="base-layout+side-menu, control-panel">
	<div data-e-component="base-layout"></div>
	<aside data-e-component="side-menu" data-e-component-id="left_menu"></aside>
	<article data-e-component="control-panel" data-e-component-required="left_menu"></article>
</div>

Order aliases

_components.order(name, value) registers an order under a name, and _components.order(name) returns it. The alias is used as the complete value of any order attribute (data-e-components-order, data-e-component-order, and the fallback ones); it cannot be combined with other steps in the same value. Register the aliases before starting the components that use them:

_components.order('dashboard', 'base-layout+side-menu, control-panel');
_components.order('html-only', 'html');

// <div data-e-components="my_dashboard" data-e-components-order="dashboard">…</div>
// <div data-e-component="notice" data-e-component-order="html-only"></div>

_components.order('dashboard'); // 'base-layout+side-menu, control-panel'

4. Lifecycle and states

The component instances returned by .ref() (or _components.get(id)) expose:

  • id (String): The instance’s final ID in the registry.
  • element (HTMLElement): The associated DOM element.
  • options (Object): The instance’s resolved options.
  • on(event, callback), once(event, callback), off(event, callback), and emit(event, data): Subscribing to and sending instance events (see section 5).
  • status(): Returns the instance’s current state:
    • "pending": Registered and not started yet. It is a momentary state, because loading starts when the instance is created (a coordinator’s children are created when their step arrives). It is also what status() returns for a destroyed instance (for example, because its element left the DOM).
    • "loading": Waiting for its required components, or downloading and applying its resources.
    • "loading-fallback": The main load has failed, and the fallback component’s load is starting. It is a momentary state that is reported to the state observer (section 6): the fallback instance, which uses the same ID, immediately moves to "loading", and that is the state status() returns while it loads.
    • "ready": Load completed and JS run without errors (a CSS or HTML failure only produces a warning and does not prevent it).
    • "failed": Final failure: its JS failed (and so did its fallback, if it had one), or one of its dependencies failed. The element gets its original attributes and content back.

Coordinators return a simpler object, with id, element, and options; their state is tracked with the state observer (section 6) or by declaring them in data-e-component-required.

Advanced API (internal): _destroy(isReset) disconnects the instance from the DOM observer, runs its cleanup tasks, and removes it from the registry. The library calls it on its own when the element leaves the DOM or when _components.resetCache() is called; the isReset parameter prevents the warning that is logged if the element is still connected. As the _ prefix indicates, it is not part of the stable API.

5. Instance events

Each component instance lets you add listeners with on(), once(), and off():

var inst = _components(document.getElementById('greeting')).ref();

if (inst) {
	// The component has finished loading
	inst.on('ready', function(data) {
		// data is undefined, or { replacedBy: instance } if the fallback was loaded
		console.log('Component inserted into the DOM.');
	});

	// Final failure: network, timeout, exception in its JS, or failed dependency
	inst.on('error', function(err) {
		console.error('Component failure:', err.message);
	});

	// Custom event, sent with _components.emit('greeting', 'refresh', data)
	inst.on('refresh', function(data) {
		console.log('Data received:', data);
	});
}

The error event always receives an Error object; if it comes from an exception in the component’s JS, its name is the component ID. If the instance is already "ready" when the listener is added (for example, because all its resources were cached), ready is not emitted again: check status() first. A coordinator’s children exist only from the moment their step starts; before that, _components.get(id) returns undefined.

Event queue

Events sent with _components.emit() to a component that does not exist yet or is not in the "ready" state are stored in a queue, with a maximum of 50 per ID (further ones are discarded with a warning in the console). When the component reaches "ready", the queue is flushed in order and synchronously, before ready is emitted; this way, the component’s JS can register its listeners with _components.get(id).on() and receive the events sent earlier. If the component moves to "failed", the queued events are discarded, and any events sent later are discarded with a warning.

6. Global methods

The library exposes these functions on the _components object:

  • _components.get(id): Returns the instance registered with that ID, or undefined.
  • _components.emit(targetId, event, data): Sends an event to a component instance. If it is not ready yet, the event is stored in the queue (see section 5). If the ID belongs to a coordinator, it logs a warning to the console and discards the event.
  • _components.order(name, value?): Registers or returns a load order alias (see section 3). Registering an alias again replaces its value for subsequent loads.
  • _components.scan(root?): Initializes the coordinators ([data-e-components]) inside root, not including root itself, or inside document.body if no root is given. It skips elements that already have a registered instance (calling it several times does not duplicate them) and coordinators that are inside a component, or on it, when that component belongs to another coordinator or is itself a coordinator: those start when the component loads. Once started, each coordinator also starts its direct sub-coordinators that are not inside one of its components. Components that are not inside a coordinator are initialized with _components(element).
  • _components.autoScan(): Runs _components.scan() when the document is ready (immediately, if it already is).
  • _components.resetCache(): Frees memory. It destroys all instances in the registry, stops the DOM observer, clears the resource caches (subsequent loads download and apply the CSS and JS again) and the event queue, and removes the registered state observers. It keeps the global configuration and the order aliases, and it does not remove styles that were already inserted.

State observer (advanced API)

_components._registerStateObserver(fn) and _components._unregisterStateObserver(fn) let you receive all state changes of components and coordinators, for example for telemetry or a global loading bar. The library uses them internally to resolve dependencies; as the _ prefix indicates, they are not part of the stable API.

function stateMonitor(id, newState) {
	console.log('[Lifecycle] Component "' + id + '" changed to state: ' + newState);
}

// Register
_components._registerStateObserver(stateMonitor);

// Unregister
// _components._unregisterStateObserver(stateMonitor);

7. Technical details

Shared requests and cache: Simultaneous requests for the same resource (same type and URL) share a single download. Responses are stored in an in-memory cache of up to 100 entries; when the limit is exceeded, the oldest entry that is not in progress is removed (if all of them are, the limit is temporarily exceeded). Cached HTML is inserted again without a new request.

Retry after failure: When downloading or applying a resource fails (network error, timeout, or an exception while running it), the error is reported to all instances that were waiting for that resource, and the entry is removed from the cache. This way, a later attempt for the same resource makes a new request instead of reusing the error.

Errors in component JS: Each component’s JS code is wrapped in a try/catch block before it runs; that is why its top-level let, const, and class declarations are not global (var and function declarations are). If it throws an exception, the library tags it with the component ID (in e.name) and rethrows it, so it appears in the browser console; a value that is not an object (e.g., throw 'text') is first converted into an Error with that message. A global error listener recognizes those exceptions, and the component’s load is considered failed.

Global error listener: The error listener that the library registers on window only reacts to exceptions tagged by the library and ignores the rest, including errors without event.error, such as those from cross-origin scripts.

Fallback and event handover: If the JS of a component that has a fallback fails, the library removes the failed instance from the registry and creates the fallback instance with the same ID. Queued events and the original instance’s listeners are transferred to the new one, except those for ready and error: those stay on the original instance, which emits them when the fallback finishes (ready receives { replacedBy: fallbackInstance }). From then on, _components.get(id) returns the new instance, and the previous reference no longer accepts on(), once(), off(), or emit() (it logs a warning).

Cleanup when leaving the DOM: The library uses a single MutationObserver on the document’s body, which checks after every change in the tree whether each instance’s element is still in the DOM. When it has been removed (for example, when switching views with a router), its _destroy() is called: the instance leaves the registry and stops waiting for its dependencies.
