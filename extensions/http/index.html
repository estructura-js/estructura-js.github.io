HTTP

Descripción

Librería de bajo nivel para peticiones HTTP asíncronas basada en el objeto nativo XMLHttpRequest. Permite controlar el ciclo de vida de cada petición: tiempo de espera (timeout), cabeceras personalizadas, credenciales de origen cruzado, progreso de subida y descarga, y cancelación. Se puede usar con callbacks o con promesas (async/await).

Librería: estructura.http.js

Compatibilidad: ES3/ES5+

Estado: RC2

Licencia: AGPL v3

Importación:
<!-- EXTENSIÓN: Estructura / HTTP -->
<script src="https://estructura.okzgn.com/extensions/http/estructura.http.js"></script>

Documentación

Inicio rápido

Una petición GET que recibe la respuesta JSON ya parseada; cualquier fallo (HTTP, red, tiempo agotado o JSON inválido) llega a onError.

_http({
	url: '/api/usuarios',
	responseType: 'json',
	onSuccess: function(usuarios) {
		console.log('Usuarios:', usuarios);
	},
	onError: function(err) {
		console.error('Fallo (' + err.type + '):', err.message);
	}
});

1. Uso y valor devuelto

La librería expone una única función global, _http.

_http(options):

Inicia una petición configurada según el objeto options.

Sintaxis:

var req = _http({ url: './config.json' });
// req.abort();
// req.getXHR();
// var res = await req; // dentro de una función async; o req.then(...), req.catch(...), req.finally(...)

Devuelve de forma síncrona un objeto de control con los siguientes métodos:

  • abort(): Cancela la petición en curso y, si está definido, invoca onAbort.
  • getXHR(): Devuelve el objeto XMLHttpRequest subyacente, para inspeccionarlo o manipularlo a bajo nivel.
  • then(onFulfilled, onRejected), catch(onRejected) y finally(fn): Solo presentes si el entorno dispone de Promise. Hacen del objeto de control un thenable, por lo que puede usarse directamente con await. Devuelven una promesa nativa, no el objeto de control: guarde este último si necesita abort(). La promesa interna solo se crea al invocar alguno de estos métodos (si la petición ya terminó, se resuelve de inmediato con ese desenlace); por eso, si solo se usan callbacks, no se producen avisos de unhandled rejection.

En entornos sin Promise (ES3/ES5), el objeto de control solo tiene abort() y getXHR(). Los callbacks reciben los mismos argumentos con o sin Promise, y se pueden combinar con then o await en la misma petición.

Valor de resolución: { data, text, status, headers, xhr }.

  • data: El cuerpo parseado como JSON si responseType es 'json' o si la cabecera Content-Type de la respuesta es JSON (por ejemplo application/json o application/problem+json); un cuerpo vacío produce null. Si en este segundo caso el parseo falla, contiene el texto crudo.
  • text: El texto crudo de la respuesta (responseText), siempre sin transformar.
  • status: El código de estado HTTP.
  • headers: Objeto con las cabeceras de la respuesta, con nombres en minúsculas (los valores repetidos se unen con ", ").
  • xhr: La instancia XMLHttpRequest.

Valor de rechazo: Una instancia de Error con las propiedades type ('http', 'network', 'timeout', 'abort' o 'parse'), status y xhr. Es el mismo tipo de objeto que recibe onError. Con type: 'http', el cuerpo de la respuesta de error está en error.xhr.responseText.

Nota: Si las opciones no son válidas (no es un objeto, o url no es un String no vacío), la extensión lanza una excepción que el núcleo de Estructura captura y muestra en la consola, con hasta un segundo de retraso; la llamada devuelve igualmente un objeto, pero sin métodos (abort, getXHR, then...). En ese caso no hay petición, ni callbacks, ni promesa, y un await sobre ese objeto no lanza: devuelve el propio objeto vacío. Lo mismo ocurre si falla la preparación de la petición, por ejemplo con un method no válido o un data con referencias circulares.

2. Opciones

El objeto options admite las siguientes propiedades:

Sintaxis:

_http({
	url: 'https://backend.com/api/v1/setData',
	method: 'POST',
	data: { 'a': '1', 'N': '...' }
});
  • url (String): La dirección del recurso. Requerida. Nota: Si se omite, no es un String o está vacía, se lanza una excepción antes de abrir la petición (ver la nota sobre opciones inválidas en la sección 1).
  • method (String): El método HTTP (ej. "GET", "POST", "PUT", "DELETE"). Por defecto, "GET".
  • headers (Object): Pares clave-valor con las cabeceras que se añaden a la petición mediante setRequestHeader.
  • data (Any): Cuerpo de la petición. Si se omite, se envía sin cuerpo (null). Acepta cadenas de texto, objetos y arrays planos, instancias de FormData, URLSearchParams, objetos Blob, documentos y búferes binarios (ArrayBuffer y sus vistas). Nota: Salvo en GET y HEAD (que no envían cuerpo, y así no se fuerza una petición preflight CORS), los objetos y arrays planos se serializan con JSON.stringify() (si JSON está disponible) y se añade la cabecera Content-Type: application/json;charset=UTF-8, salvo que headers ya defina un Content-Type (la comparación no distingue mayúsculas). El resto de tipos, incluidas las cadenas ya serializadas, se pasan sin transformar al método send() nativo; si envía una cadena JSON, defina usted el Content-Type en headers. Con FormData, se recomienda no definir Content-Type en headers para que el navegador añada el tipo multipart con su límite (boundary). data no se añade a la URL: con GET o HEAD el navegador no envía cuerpo, así que los parámetros deben ir en url.
  • responseType (String): Con el valor 'json', el cuerpo de una respuesta exitosa se parsea como JSON antes de entregarse: onSuccess recibe el valor parseado (un cuerpo vacío produce null) y, si el parseo falla, se invoca onError con un error de tipo 'parse' en lugar de onSuccess. No modifica la propiedad nativa xhr.responseType, por lo que xhr.responseText sigue disponible. Si se omite, onSuccess recibe el texto crudo. Cualquier otro valor se ignora: la respuesta se lee siempre como texto, por lo que la librería no sirve para descargas binarias.
  • timeout (Number): Límite de tiempo en milisegundos. Con 0 (valor por defecto) no hay límite.
  • withCredentials (Boolean): Con true, envía credenciales (cookies, cabeceras de autorización) en peticiones de origen cruzado (CORS).

3. Callbacks

Los callbacks también se definen en options y se invocan en distintas etapas de la petición:

Estado y finalización:

  • onSuccess(response, xhr): Se invoca cuando la petición termina con un código de estado entre 200 y 299. Recibe como primer argumento el texto de la respuesta o, con responseType: 'json', el valor ya parseado (por ejemplo, un objeto), y como segundo la instancia XHR. Sin responseType: 'json' recibe el texto aunque la respuesta tenga Content-Type JSON: el parseo automático según esa cabecera solo se aplica a data en la promesa.
  • onError(error, xhr): Se invoca ante fallos de red o bloqueos del navegador (CORS, estado 0), respuestas con estado fuera del rango 2xx (incluidas las 3xx que el navegador no haya seguido, y las 4xx y 5xx), fallos de parseo con responseType: 'json' y tiempos de espera agotados si no se define onTimeout. Recibe como primer argumento una instancia de Error con las propiedades type ('http', 'network', 'timeout' o 'parse'), status y xhr, y como segundo la instancia XHR.
  • onHeadersReceived(headersString, xhr): Se invoca cuando se reciben las cabeceras de la respuesta (readyState === 2). Recibe la cadena cruda que devuelve getAllResponseHeaders().
  • onReadyStateChange(readyState, status, xhr): Listener de bajo nivel que se invoca en cada cambio de readyState posterior a la apertura: 2, 3 (puede repetirse mientras llega la respuesta) y 4.

Progreso y cancelación:

  • onProgress(loaded, total, percent): Se invoca durante la descarga de la respuesta cuando el tamaño total es conocido (propiedad lengthComputable del evento). Recibe los bytes recibidos, los bytes totales y el porcentaje. Nota: lengthComputable depende de que la respuesta incluya la cabecera Content-Length; sin ella, no se invoca.
  • onUploadProgress(loaded, total, percent): Igual que onProgress, pero para la subida del cuerpo de la petición. Se registra en xhr.upload si el navegador lo ofrece. Nota: Registrar listeners en xhr.upload obliga al navegador a enviar una petición previa (preflight) CORS en las peticiones de origen cruzado, por lo que el servidor debe responder a OPTIONS.
  • onTimeout(xhr): Se invoca al superarse el límite de timeout. Si se omite, el error se entrega a onError con type: 'timeout'.
  • onAbort(xhr): Se invoca cuando la petición se cancela con el método abort() del objeto de control.

4. Desenlace y errores

Aviso al combinar callbacks:

Si se define onReadyStateChange junto con onSuccess, onError u onHeadersReceived, la librería muestra una advertencia en la consola. Es solo informativa: todos los callbacks se siguen invocando de forma independiente, por lo que conviene no gestionar los mismos estados en ambos.

Desenlace único:

Cada petición tiene un único desenlace: éxito, error, tiempo agotado o cancelación. Se registra el primero que ocurre y se ignoran los eventos nativos posteriores. Por ello, de onSuccess, onError, onTimeout y onAbort solo se invoca uno, una sola vez, y la promesa se resuelve o rechaza con ese mismo desenlace. onReadyStateChange, onHeadersReceived y los callbacks de progreso no forman parte del desenlace y se siguen invocando con normalidad.

  • Estado 200–299: onSuccess; la promesa se resuelve.
  • Estado distinto de 2xx y mayor que 0: onError; rechazo con type: 'http'.
  • Fallo de red, CORS o bloqueo (estado 0): onError; rechazo con type: 'network'.
  • Tiempo agotado: onTimeout (o onError si no existe); rechazo con type: 'timeout'.
  • Cancelación con abort(): onAbort; rechazo con type: 'abort'.
  • JSON inválido con responseType: 'json': onError; rechazo con type: 'parse'.

Estado 0:

Las peticiones que no llegan a comunicarse con el servidor (fallo de DNS, pérdida de conexión, bloqueo por CORS u otras restricciones del navegador) terminan con status igual a 0. Según la especificación de XMLHttpRequest, los eventos nativos error, timeout y abort se disparan después del cambio a readyState === 4. Por eso, al detectar ese estado con código 0, la librería difiere la decisión con setTimeout(0): si en ese intervalo alguno de esos eventos ya resolvió la petición, se respeta su desenlace (fallo de red, tiempo agotado o cancelación); si no, se invoca onError con el error 'Request failed with status 0 (network/CORS/blocked): ' + url. Así, todo fallo con estado 0 se notifica exactamente una vez. Nota: Algunos navegadores devuelven estado 0 en peticiones exitosas a URLs file://; la librería las trata igualmente como error de red.

Cancelación:

El método abort() detiene la petición en curso. Aunque la cancelación deja el estado nativo en 0, el evento abort se registra antes de que venza la espera diferida del estado 0; si el navegador no despacha ese evento, el propio método abort() registra la cancelación. En ambos casos solo se invoca onAbort, nunca onError. Llamar a abort() sobre una petición ya terminada no cambia su desenlace, aunque el navegador reinicia el objeto XHR (status pasa a 0 y responseText queda vacío). El valor de resolución de la promesa no se ve afectado: el texto, el estado y las cabeceras se guardan en el momento del éxito.

5. Ejemplos

Petición GET con respuesta JSON

Con responseType: 'json', onSuccess recibe el valor parseado y un JSON inválido llega a onError como type: 'parse'. Sin responseType, onSuccess recibe el texto crudo: es lo adecuado para respuestas que no son JSON, o para parsear a mano y tratar un JSON inválido sin pasar por onError.

_http({
	url: 'https://api.ejemplo.com/v1/usuarios',
	method: 'GET',
	responseType: 'json',
	onSuccess: function(usuarios, xhr) {
		console.log('Lista de usuarios procesada:', usuarios);
	},
	onError: function(err, xhr) {
		// err.type: 'http' | 'network' | 'timeout' | 'parse'
		console.error('Fallo (' + err.type + '):', err.message);
	}
});

Envío POST con progreso y tiempo límite

var controlEnvio = _http({
	url: 'https://api.ejemplo.com/v1/archivos',
	method: 'POST',
	headers: {
		'X-Client-Identifier': 'Estructura-App'
	},
	// Se serializa como JSON y se añade Content-Type: application/json;charset=UTF-8
	data: { archivoId: 'doc_09182' },
	timeout: 10000,
	onUploadProgress: function(cargado, total, porcentaje) {
		console.log('Progreso del envío de datos: ' + porcentaje.toFixed(2) + '%');
	},
	onSuccess: function(respuesta, xhr) {
		console.log('Procesamiento completado con éxito:', respuesta);
	},
	onTimeout: function(xhr) {
		console.error('El servidor superó el límite de respuesta de 10 segundos.');
	},
	onError: function(err, xhr) {
		console.error('No se pudo completar el envío:', err.message);
	}
});

Cancelación de una petición

var peticion = _http({
	url: 'https://api.ejemplo.com/v1/stream-datos',
	onSuccess: function(respuesta, xhr) {
		console.log('Datos recibidos:', respuesta);
	},
	onAbort: function(xhr) {
		console.log('La petición se canceló antes de terminar.');
	}
});

// Cancelar la petición cuando el usuario pulsa un botón
document.querySelector('#cancelar-accion').addEventListener('click', function() {
	peticion.abort();
});

Uso con promesas y async/await (ES6+)

En entornos con Promise, el objeto de control devuelto por _http() se puede esperar directamente. Los callbacks siguen siendo opcionales y compatibles con este uso:

async function obtenerDatosDeUsuario() {
	try {
		var respuesta = await _http({
			url: 'https://api.ejemplo.com/v1/perfil',
			timeout: 5000
		});
		// data va parseado si el servidor responde con Content-Type JSON
		console.log('Datos obtenidos:', respuesta.data, respuesta.status, respuesta.headers['content-type']);
	}
	catch (error) {
		// error.type: 'http' | 'network' | 'timeout' | 'abort' | 'parse'
		console.error('Error capturado con async/await (' + error.type + ', ' + error.status + '):', error.message);
	}
}

// También con then/catch/finally, conservando el control de cancelación
var peticion = _http({ url: '/api/estado' });
peticion
	.then(function(respuesta) { console.log(respuesta.text); })
	.catch(function(error) { console.error(error.type); })
	.finally(function() { console.log('Fin'); });
// peticion.abort();

6. Características técnicas

Cabeceras propias: De headers solo se envían las propiedades propias del objeto; las heredadas del prototipo se ignoran.

Cuerpo sin transformar: Salvo los objetos y arrays planos, que se serializan como JSON, data se pasa tal cual a send(), de modo que el navegador determina las cabeceras asociadas (por ejemplo, el límite de multipart/form-data con FormData).
