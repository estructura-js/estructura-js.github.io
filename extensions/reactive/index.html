Reactive

Description

Provides two-way data binding between a state object and the DOM. It synchronizes the script’s state with the user interface through templates with configurable delimiters (by default, {{ variable }}). DOM updates are batched and applied asynchronously, in a microtask.

Library: estructura.reactive.js

Compatibility: ES6+

Status: RC2

License: AGPL v3

Import:
<!-- EXTENSION: Estructura / Reactive -->
<script src="https://estructura.okzgn.com/extensions/reactive/estructura.reactive.js"></script>

Documentation

1. Initialization and state

Initialize reactivity by passing any DOM element as the root (usually the view’s container) or document, in which case document.documentElement is used. Templates are compiled and rendered for the first time synchronously when the instance is created. Access the reactive state through the Proxy object returned by the .state() method.

// Initialize reactivity on the document
var myReactive = _reactive(document.documentElement);

// Get the state object
var state = myReactive.state();

// Write properties to the state
state.myVariable = 'Hello World';
// The DOM is updated in the next microtask, not on this line

Reserved names: on, off, stop, and event are methods of the state and cannot be used as variables: assigning them throws an error. Symbol keys are not supported either.

Initialization failures: if the root is not a valid node, the configuration is not an object, or a template is invalid (for example, a two-way binding with two variables), _reactive() does not throw the error: it shows it in the console with a delay of up to one second and returns an object without the state() method.

Nested roots: avoid creating an instance inside another instance’s root. The first one to compile a template replaces it with its value, and the other one can no longer find it.

2. Advanced configuration

The constructor accepts an optional second argument (Object) to configure custom template delimiters and processors for names and expressions.

Configuration options:

  • variables_prefix (String): the template’s opening delimiter (default: "{{").
  • variables_postfix (String): the template’s closing delimiter (default: "}}").
  • variables_preprocessor (Function): a callback that runs when each template is extracted. It receives the text between the delimiters (without leading or trailing spaces) and a metadata object ({ expr, start, end }). Whatever it returns is used as the variable name (or as the expression text); if it returns a falsy value, the template is ignored and stays as literal text.
  • variables_processor (Function): a callback that computes the initial value of an expression. It runs only once, when the expression is registered. It receives the virtual key (String), the expression text (String), and the state (Object), and whatever it returns is stored in the state.
  • sanitizer (Function | false): the instance’s own sanitizer for values interpolated into attributes, instead of _reactive.sanitize. With false, sanitization is disabled for this instance (see Sanitization).

Configuration example:

var myReactive = _reactive(document.documentElement, {
	variables_prefix: '[[',
	variables_postfix: ']]',
	variables_preprocessor: function(name, meta){
		// Ignore specific variables by returning a falsy value
		if(name === 'ignore_me') return null;
		return meta.expr ? name : name.toLowerCase();
	},
	variables_processor: function(key, expr, state){
		try {
			var keys = Object.keys(state);
			var vals = keys.map(function(k){ return state[k]; });
			return new Function(keys, 'return (' + expr + ')').apply(null, vals);
		} catch(e){ return ''; }
	}
});

Warning: evaluating expressions with new Function is equivalent to using eval. It requires a Content Security Policy that allows 'unsafe-eval', and it must never be used with templates that may contain user content.

3. Templates and expressions

The library automatically classifies the text between delimiters into two categories:

  • Simple identifiers: if the text (without leading or trailing spaces) contains only ASCII letters, digits, _, or $, and does not start with a digit (e.g., firstName, my_variable), it is registered directly as a state variable and is updated every time that variable changes. A name with accented letters or ñ (año) is treated as an expression.
  • Expressions: if the text contains operators, internal spaces, or object paths (e.g., user.name or a + b), it is treated as an expression and assigned a virtual key based on its position within the text (e.g., _e_7_18). The same expression always uses the same key, even in different nodes; if two different expressions occupy the same position, the second one gets a suffix (e.g., _e_7_18_2). The preprocessor also receives expressions, with meta.expr set to true.

Important: the value of an expression is computed only once, when it is registered, through variables_processor (without a processor, it stays empty). It is not recomputed when the variables it uses change: in {{a + b}} or {{user.name}}, modifying state.a or state.user does not update the rendered text. In addition, the processor only sees the values the state has at that moment. To change what an expression shows, assign the new value to its virtual key (variables_processor and the createdVariable event receive it) or, better, compute the value in JavaScript and use a simple variable.

One-way binding

Applies to text nodes and to regular attributes (such as class, src, id, etc.). Supports several variables or expressions in the same text. For the boolean attributes disabled, checked, readonly, required, and selected, a falsy value (or the text 'false') removes the attribute, and any other value adds it. Other boolean attributes (such as hidden or open) are treated as regular attributes: they stay present even if the value is empty.

<!-- Text nodes with identifiers and expressions -->
<h1>Welcome, {{firstName}} {{lastName}}</h1>
<p>Operation: {{1 * 2}}</p>
<p>Nested path: {{user.name}}</p>

<!-- Attributes -->
<div class="alert {{alert_type}}" id="{{record_id}}"></div>
<button disabled="{{locked}}">Send</button>

Two-way binding

Carries the changes the user makes in the interface into the state, through the root node’s input and change events. Applies to the value attribute (or checked on checkboxes and radio buttons) and to the text of <textarea> elements. In the other direction, every state change is reflected in the control, including a <textarea> that the user has already edited. These bindings support only one variable: with more than one, initialization fails (see Initialization failures).

<!-- Text input -->
<input type="text" value="{{myVariable}}">

<!-- Boolean control -->
<input type="checkbox" checked="{{active}}">

<!-- Textarea -->
<textarea>{{myVariable}}</textarea>

4. Lifecycle

The state exposes methods to activate, pause, or shut down the instance.

  • state.on(): compiles the root node’s templates, renders all variables, and activates the input/change listeners and the MutationObserver. It runs automatically when the instance is created; it can be called again after stop() to resume.
  • state.stop(): removes the input/change listeners, disconnects the MutationObserver, and discards pending updates, without losing the registrations or the state data. Later assignments to the state still update the nodes that are already registered.
  • state.off(): calls stop() and then deletes the node and variable registrations. The state values are kept. Since templates that have already been rendered do not keep their delimiters, state.on() does not recover those bindings.

5. Lifecycle events

Lets you subscribe callbacks to variable and instance lifecycle events through state.event(). Each event supports a single callback: registering another one replaces the previous one. If a callback throws an error, it is rethrown with the event name in the message.

Syntax:

state.event('createdVariable', function(name){
	console.log('Registered variable:', name);
});

Supported events:

  • createdVariable: fires when a variable that does not exist in the state yet appears in the DOM. Receives the variable name (String; for expressions, their virtual key).
  • deletedVariable: fires when a variable loses all its bindings to DOM nodes. Receives the variable name (String); its value is kept in the state.
  • beforeMutateVariable: fires before a DOM node is updated. Receives the variable (String), the value about to be written (the full resulting text of the node or attribute; for boolean attributes, true or false), the containing element (Element), the node that changes (text or attribute), and the attribute name ('textContent' for text nodes).
  • afterMutateVariable: fires after the node is updated. Receives the same arguments as beforeMutateVariable.
  • reactiveOn: fires when state.on() is called. It does not fire on the initial startup, because no callbacks are registered yet at that point.
  • reactiveStop: fires when state.stop() is called, and also when state.off() is called.
  • reactiveOff: fires when state.off() is called, after reactiveStop.

6. Sanitization

Every time an interpolated attribute is rendered (except boolean ones), the resulting text goes through _reactive.sanitize(value, ctx) before it is written, where ctx is { type: 'attribute', name, element, variable }. The function returns the value that is finally written (which is also the value the beforeMutateVariable/afterMutateVariable events receive). Text nodes do not go through it.

What is filtered by default:

  • In URL attributes (href, src, action, formaction, xlink:href, poster, cite, background), the javascript: and vbscript: schemes are neutralized: '' is written and a console.warn is emitted.
  • data: is allowed only in src and poster, and only for data:image/, data:video/, or data:audio/; otherwise, it is neutralized in the same way.
  • To compare the scheme (without changing the value that is written), spaces and control characters are removed and the text is lowercased, since browsers accept variants such as java\tscript:.
  • Any interpolated attribute whose name starts with on (case-insensitive) is blocked, whether or not it is an event handler, such as onclick="{{action}}": '' is written and a console.warn is emitted. The only exceptions are attributes that match a boolean property of the element (native elements have none that starts with on; it can happen with custom elements).

What is not filtered, and why: text (textContent, already safe), value and checked (two-way binding: altering them would desynchronize the state), boolean attributes, class, id, style, data-*, and aria-*, because they do not execute code. HTML sinks (srcdoc) pass through unchanged: filtering HTML reliably requires a full parser, so that is left to a specialized library.

Replace or extend: assign your own function to _reactive.sanitize (it affects all instances that do not define sanitizer), or use the per-instance sanitizer option. To keep the default rules, save the original and call it from the new one.

HTML:

<div id="app">
	<a href="{{link}}">Link</a>
	<iframe srcdoc="{{content}}"></iframe>
</div>
<div id="panel"><a href="{{destination}}">Trusted content</a></div>

JavaScript:

// Connect DOMPurify for the HTML sinks, keeping the default rules
var sanitizeDefault = _reactive.sanitize;

_reactive.sanitize = function(value, ctx){
	if(ctx.name === 'srcdoc'){ return DOMPurify.sanitize(String(value)); }
	return sanitizeDefault(value, ctx);
};

var state = _reactive(document.getElementById('app')).state();
state.link = 'java\tscript:alert(1)'; // Writes '' and logs a warning to the console

// Disable sanitization on a specific instance (#panel is outside #app)
var trusted = _reactive(document.getElementById('panel'), { sanitizer: false });

7. Technical details

Asynchronous updates in microtasks: assignments to the state do not update the DOM immediately. They are batched and applied together in a microtask (Promise.resolve().then), so after state.x = 1 the DOM has not changed yet. To read the updated DOM, wait for a microtask (for example, await Promise.resolve() inside an async function). Assigning a variable the value it already has does not trigger an update.

Synchronous initial compilation: when the instance is created (or when state.on() is called), templates are compiled and rendered in the same step.

MutationObserver: detects nodes and attributes added, removed, or modified inside the root node, registers new templates, and removes deleted nodes from the registry. Nodes added after startup are registered, but they are not rendered until one of their variables next changes. Before a node is updated, the library checks whether it is still connected (.isConnected); disconnected nodes are removed from the registry instead of being updated.

Memory: the library uses WeakMap to associate templates and registrations with nodes, so nodes removed from the registry can be freed.
