Handlers

Description

Associates DOM elements with JavaScript functions (handlers) through data-e-handler-* attributes. Each element has its own state context and can run its handlers in sequence or as a middleware chain, and each handler can trigger others when it marks a success or error result. The library also controls event propagation between elements and lets you unmount elements from the DOM and mount them again.

Library: estructura.handlers.js

Compatibility: ES5/ES6+

Status: RC3

License: AGPL v3

Required dependency: estructura.events.js (Events, documentation). Handlers uses the global _events object to register DOM listeners, so Events must be loaded first; if it is not available, Handlers throws an exception when it loads.

Import:
<!-- DEPENDENCY: Estructura / Events -->
<script src="https://estructura.okzgn.com/extensions/events/estructura.events.js"></script>

<!-- EXTENSION: Estructura / Handlers -->
<script src="https://estructura.okzgn.com/extensions/handlers/estructura.handlers.js"></script>

Documentation

Quick start

Declare the handler and its event in the HTML, register the function with _handlers(), and call .start() once the element exists in the DOM:

<button data-e-handler="greet" data-e-handler-id="btn-greet" data-e-handler-event="click">Greet</button>

<script>
_handlers({
	greet: function (event) {
		this.liveElement.textContent = 'Hello';
	}
}).start();
</script>

1. Initialization and methods

The library exposes the global function _handlers. It relies on _events to register the elements’ listeners.

Syntax:

_handlers(...handlersMapsOrStrings).start(startNode?);

Arguments:

  • handlersMapsOrStrings (Object / String): One or more arguments. Each object maps handler names to JavaScript functions; a String imports a group of handlers previously registered with .public(name). The arguments are merged from left to right; if a name is repeated, the first one is kept and a warning is logged to the console. If a String does not match any registered group, or an argument is not an object, the error is shown in the console and the returned object has no methods (calling .start() throws a TypeError).
  • Shortcuts: If the value of a key is a String or an array of handler names (instead of a function), that key is a shortcut that expands to those handlers. For example, { 'triple-step': ['step', 'step', 'step'] }. Shortcuts can be nested; a circular reference produces an error.

Methods:

Calling _handlers(...) returns an object with the .start(), .end(), and .public() methods. The global _handlers function also exposes .console() and .errors():

  • .start(startNode?): Finds the elements with data-e-handler in the DOM and initializes them. If startNode is omitted, the whole document is processed.
    • Scope: startNode (a Node or a CSS selector in a String) limits the search to that element and its descendants. If startNode itself has data-e-handler, it is processed too (and then it needs data-e-handler-id); otherwise, it acts only as a container.
    • Groups: Every handler that appears in the scope must be in the group; otherwise, .start() fails with Unknown handler. To have several groups on one page, start each one with its own startNode.
    • Repeated calls: The list of nodes found is stored per startNode (the same Node, the same selector, or no argument), even if it is empty, and all groups share it; that is why .start() must be called once the elements exist. A second .start() on the same startNode reuses that list and does not duplicate the listeners, but it runs the data-e-handler-start and data-e-handler-end-start handlers again. To scan again, call .end() with the same argument first.
  • .end(startNode?): The reverse of .start(). Removes the listeners registered with _events (delegated and local) from the elements found in the given scope and deletes the state contexts of the handlers in their data-e-handler, including those written in the handler.id form (the contexts of handlers that appear only in -connect, -success, or -error are kept). It does not remount unmounted elements.
  • .public(name): Registers the group of handlers under name, a String of 1 to 128 characters. If the name is already registered, it does not replace it and shows an error in the console. After that, _handlers('name', ...) imports those handlers by name.
  • _handlers.console(on): Controls the library’s console messages. true enables log, info, warn, and error; false silences all of them. It also accepts the names of the channels to enable: _handlers.console('warn', 'error') enables those two without disabling the others, so to keep only those, call _handlers.console(false) first. Enabled by default.
  • _handlers.errors(on): With true (the default), library errors (unknown handler, missing required attribute, exception inside a handler…) interrupt the operation in progress; with false, they are ignored silently and execution continues. The _events dependency check, which runs when the library loads, always throws its exception.

Errors:

Errors in .start(), .end(), and .public() do not reach the calling code: the Estructura core catches them and shows them in the console, with a delay of up to one second, as Estructura (handlers): Method "start" error: …. The method stops at that point: if it is .start(), the remaining elements are left unprocessed and no listener is registered, because listeners are registered at the end. Errors in a handler run by an event appear in the console as an uncaught exception from the listener.

2. HTML attributes

Handlers are associated with elements through the following data-* attributes:

  • data-e-handler (String): Required. List of handlers or shortcuts, separated by commas or spaces. A dot (.) or a vertical bar (|) separates the handler name from an instance ID: status.notice runs the status handler with the context (this) of the notice instance if it exists, and otherwise with the element’s own context. With several IDs (status.notice.summary), the handler runs once for each one. That is why a handler name cannot contain dots or vertical bars.
  • data-e-handler-id (String): Required. The element’s instance ID. The library removes whitespace ("btn - signup" becomes "btn-signup"). Each handler keeps its own state context for each ID. Use a different ID on each element: if two elements share an ID and a handler, both use the context created for the first one (with its liveElement).
  • data-e-handler-event (String): Optional. The DOM event or events that run the handlers, separated by commas or spaces (e.g., "click", "submit", "click focusout"). If present, it cannot be empty. The part after a dot (such as .test in dblclick.test) is ignored, because the library assigns its own namespace to each instance.
  • data-e-handler-middleware (Boolean): Optional. If present, the element’s handlers (including those in data-e-handler-start and data-e-handler-end-start) run in middleware mode (see section 5).
  • data-e-handler-propagation (Boolean): Optional. By default, when a bubbling event runs an element’s handlers, the handlers of ancestor elements for that same event do not run. If the element whose handlers ran includes this attribute, execution continues to the next ancestor with handlers for that event; to go further up, that ancestor also needs the attribute. Only the attribute counts: calling event.stopPropagation() inside a handler does not change this behavior.
  • data-e-handler-ignore (Boolean): Optional. If present, the element is unmounted on start (it is replaced by a comment), its events are not registered, and the elements with handlers inside it are not processed. Its context offers only mount(), unmount(), and mounted, and it is used from outside (see section 4). After mount(), the element returns to the DOM, but its handlers do not respond to events until .end() is called on its scope, followed by .start() again.
  • data-e-handler-start (String): Optional. Handlers that run immediately when the element is processed, with an empty object instead of the event. If the attribute is empty, all the handlers in data-e-handler run.
  • data-e-handler-end-start (String): Optional. Same as the previous one, but the handlers run at the end of .start(), once all the elements have been processed and their listeners registered.

3. Per-handler attributes

For each handler, the library also reads attributes whose names are built from the handler name in kebab-case. For example, for the myRequest handler the attributes are data-e-my-request-success, data-e-my-request-error, etc. They are read from the copy of the element taken in .start() (this.initialElement), so changing them later has no effect until .end() is called, followed by .start() again. In the -success, -error, and -connect lists, the handler.id form limits execution to the id instance of that handler.

  • data-e-[handler]-success: Handlers that run when a value is assigned to this.success.
  • data-e-[handler]-error: Handlers that run when a value is assigned to this.error.
  • data-e-[handler]-connect: Handlers connected to this one, which the handler can invoke with this.connect() (see below). On start, the library creates a context for each of them under this element’s ID.
  • data-e-[handler]-middleware: If present, this handler’s -success and -error handlers run in middleware mode.

Connections with this.connect(state, data, ids?)

this.connect() acts on the instances of the handlers listed in data-e-[handler]-connect. Without ids, it reaches all the instances of those handlers (those of any element); with ids (a String or an array of instance IDs), only those. Its effect depends on the arguments:

  • this.connect(value) (without data): runs each connected handler with value as the first argument and with the context (this) of the target instance.
  • this.connect('property', value): assigns value to this.property in the context of each target instance. With 'success' or 'error', the assignment triggers its -success or -error chain.

The reserved names (liveElement, initialElement, connect, ready, mount, unmount, and mounted) cannot be used as state: the call is skipped with a warning in the console.

<p data-e-handler="status" data-e-handler-id="notice"></p>
<button data-e-handler="send" data-e-handler-id="btn-send" data-e-handler-event="click"
	data-e-send-connect="status">Send</button>

<script>
_handlers({
	send: function (event) {
		// Runs "status" only on the "notice" instance (the paragraph)
		this.connect('Sending…', undefined, 'notice');
		// Assigns this.lastSent on that same instance
		this.connect('lastSent', Date.now(), 'notice');
	},
	status: function (message) {
		this.liveElement.textContent = message;
	}
}).start();
</script>

Without the third argument, status would also run on the btn-send instance that data-e-send-connect creates, and it would change the button’s text.

4. Execution context

Inside a handler, this is the instance’s state context: an object without a prototype (Object.create(null)), specific to each combination of handler and ID, where you can keep data between runs. It also offers:

  • this.liveElement (Node): The element in the DOM.
  • this.initialElement (Node): A copy (cloneNode) of the element taken in .start(). It keeps the original attributes even if the element changes later.
  • this.ready (Boolean): Set to true when the instance is registered. The library does not modify it again, so you can use it as your own flag.
  • this.mounted (Boolean): Read-only. Indicates whether the element is mounted in the DOM or unmounted with unmount() or data-e-handler-ignore. Assigning a value to it logs a warning to the console and has no effect.
  • this.mount() (Function): Inserts the element back in its original position, in place of the comment left by unmount(). Returns the element; if it cannot, it logs a warning and returns undefined.
  • this.unmount() (Function): Removes the element from the DOM and leaves a comment with the instance ID in its place. The element is kept in a DocumentFragment, which is what it returns. If the element has several handlers, use the same context for unmount() and mount(): each context keeps its own mount state, including the one that mounted reads.
  • this.success: Assigning a value to it runs the data-e-[handler]-success handlers and passes them that value. Each one runs on all of its instances, once per ID and with that instance’s context, not only on this element’s instance; to limit it, use the handler.id form in the attribute. Reading this.success does not always return the assigned value; if you need it later, store it in another property of the context.
  • this.error: Same as this.success, with the data-e-[handler]-error handlers.
  • this.connect(state, data, ids?) (Function): Acts on the connected handlers (see section 3).

From outside a handler, an instance’s context is the property named after its ID on the handler function. For example, if var myHandlers = { panel: function () { … } } is passed to _handlers(myHandlers), the context of the element with data-e-handler-id="panel-1" is myHandlers.panel['panel-1'], and myHandlers.panel['panel-1'].mount() mounts it again.

5. Execution modes

The arguments each handler receives depend on the execution mode:

Sequential mode (default)

Handlers run one after another, and each one receives the same arguments. If one throws an exception, the following ones do not run (except with _handlers.errors(false)).

  • Event handlers: Receive the DOM event (or an empty object if they run through data-e-handler-start or data-e-handler-end-start). 
    function myHandler(event) {
	// event: the DOM event, or an empty object at startup
	console.log("Source element:", this.liveElement);
}
  • Success or error handlers: Receive the value assigned to this.success or this.error. 
    function myHandlerSuccess(data) {
	// data: the value assigned to this.success or this.error
	console.log("Success data received:", data);
}

Middleware mode

It is enabled with data-e-handler-middleware (event handlers) or with data-e-[handler]-middleware (success and error handlers). The handlers form a synchronous chain: each one receives the next function and decides whether to continue, modify the data, or stop the chain. If a handler calls next later (for example, inside a promise or a setTimeout), the rest of the chain runs at that moment. The shared data object starts empty (Object.create(null)).

  • Event middleware handlers: Receive the event, the data object, and the next function. 
    function myMiddleware(event, data, next) {
	data.timestamp = Date.now();
	return next(data); // Continues with the next handler
}
  • Success or error middleware handlers: Receive the value assigned to this.success or this.error, the data object, and the next function. 
    function myMiddlewareSuccess(payload, data, next) {
	data.result = payload;
	return next(data);
}

If a handler does not call next(data), the following handlers in the chain do not run.

6. Examples

Public handlers and deferred start

// 1. Register a group of common handlers under the name "common"
_handlers({
	logger: function (event) {
		console.log("Action detected on element id:", this.liveElement.id);
	}
}).public('common');

// 2. Import "common" and merge it with local handlers
_handlers("common", {
	validator: function (event) {
		var validData = true; // Simulated validation
		if (validData) {
			this.success = { status: "valid", timestamp: Date.now() };
		} else {
			this.error = { status: "invalid" };
		}
	},
	moduleOk: function (data) {
		console.log("Flow completed with data:", data);
	}
}).start();

Imported handlers are used by their name (logger), without the group name. As in the quick start, the script above must run once the button exists in the DOM:

<!-- Each click runs the "logger" and "validator" handlers. In addition, "validator"
     runs once at the end of .start() (data-e-handler-end-start). -->
<button id="action"
	data-e-handler="logger, validator"
	data-e-handler-id="btn-send"
	data-e-handler-event="click"
	data-e-handler-end-start="validator"
	data-e-validator-success="moduleOk">
	Process form
</button>

Propagation to the parent element

<!-- The parent container responds to the click only because the child declares 'data-e-handler-propagation' -->
<div data-e-handler="parentLogger" data-e-handler-id="box-parent" data-e-handler-event="click">
	<button data-e-handler="childAction" data-e-handler-id="btn-child" data-e-handler-event="click" data-e-handler-propagation>
		Run and propagate to the parent
	</button>
</div>

<script>
_handlers({
	parentLogger: function (event) {
		console.log('Parent:', this.liveElement);
	},
	childAction: function (event) {
		console.log('Child:', this.liveElement);
	}
}).start();
</script>

7. Technical details

Event delegation: Bubbling events are caught on document.documentElement, in the capture phase, with one listener per event type. Events that do not bubble (load, unload, error, scroll, resize, abort, focus, blur, mouseenter, and mouseleave) are registered on each element. The library does not add properties to the browser’s Event objects.

Propagation defined in the HTML: Only data-e-handler-propagation decides whether a bubbling event, after running an element’s handlers, also runs those of the next ancestor with handlers; the handlers’ code does not change it. This applies only to bubbling events.

Isolated state per instance: Each combination of handler and ID has its own context, created with Object.create(null), with no inherited properties.

Mounting and unmounting: unmount() replaces the element with a comment and keeps it in a DocumentFragment; mount() returns it to the same position.

Attributes read on start: The per-handler attributes (-success, -error, -connect, -middleware) are read from this.initialElement, the copy taken in .start(); later changes to the element do not affect them.

Cycle-free shortcuts: If two or more shortcuts reference each other in a cycle, the library produces an error instead of entering an infinite loop.

Cleanup: .end() uses _events to remove the listeners of the elements in its scope and deletes the contexts of the handlers in their data-e-handler.
