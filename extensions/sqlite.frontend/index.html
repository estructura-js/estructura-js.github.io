SQLite Frontend

Description

SQLite database compiled to WebAssembly (WASM) for the browser. Operations run in a background thread (Web Worker), so they do not block the interface. Data is stored persistently in the origin private file system (OPFS) when the browser and the server headers allow it; otherwise, in memory. It offers raw SQL on strings and chainable methods on objects (a query builder), with callbacks or promises.

Library: estructura.sqlite.frontend.js

Compatibility: ES6+ / WebAssembly / Web Workers / OPFS

Status: RC2

License: AGPL v3

Required files (self-hosted): estructura.sqlite.frontend.js, estructura.sqlite.frontend.wasm.worker.js, and the _dependencies/_sqlite/ directory (official SQLite WASM v3.53.0-build1). The Worker is created with the relative path ./estructura.sqlite.frontend.wasm.worker.js, which the browser resolves relative to the page (not to the script), and the Worker imports ./_dependencies/_sqlite/index.mjs relative to itself. That is why the Worker and the _dependencies/_sqlite/ directory must be in the same directory as the HTML page that uses the library (the simplest option is to put estructura.sqlite.frontend.js there as well). A Worker can only be loaded from the same origin as the page, so these files cannot be served from a CDN.

Live demo

Click “Run demo” to create a column and insert, query, update, and delete rows in the active database; the results are shown in the browser console and, at the end, a copy of the database is downloaded (test.db.sqlite). You can also select your own .sqlite file (minimum 20 KB): the demo opens it with .open() and then runs the same operations on it.

Documentation

Quick start

The following example creates a table with one column, inserts a row, and reads it (inside an async function):

async function init() {
	await _sqlite_frontend('notes').table();
	await _sqlite_frontend({ name: 'text', type: 'TEXT' }).column();
	await _sqlite_frontend({ text: 'Hello' }).row();

	var res = await _sqlite_frontend({ '*': true }).get();
	console.log(res.get['*'].result); // [{ _auto_id: …, text: 'Hello' }]
}

init();

1. Execution model

The library exposes the global function _sqlite_frontend. All operations are sent to a Web Worker (estructura.sqlite.frontend.wasm.worker.js) that runs SQLite.

Callbacks or promises:

Each method accepts a callback as its optional first argument and a time limit in milliseconds (timeout) as its second. If the callback is omitted, the method returns a promise (Promise), usable with async/await; if a callback is passed, it returns undefined.

// 1. With promises (inside an async function or a module)
try {
	var result = await _sqlite_frontend('SELECT * FROM users').sql();
	console.log('Data:', result.sql.result);
} catch (error) {
	console.error('SQL error:', error.message);
}

// 2. With a callback
_sqlite_frontend('SELECT * FROM users').sql(function(response) {
	if (response.error) {
		console.error('Error:', response.error);
		return;
	}
	console.log('Result:', response.sql.result);
});

2. Errors

An operation’s errors arrive in the Worker’s response:

  • With promises: If the response contains a general error (response.error), the promise is rejected with an Error whose message is that text; the full response is in error.response. Errors for a specific key in .get(), .set(), or .del() do not reject the promise: it resolves, and the error is reported in response[method][key].error.
  • With callbacks: When it is invoked, the callback always receives the response object. If there was a general failure, response.error contains the message.
  • Per-key errors: When a call to .get(), .set(), or .del() includes several keys, the failure of one does not prevent the others from being processed; it is isolated in response[method][key].error. Exception: a failure in a global update with .set() (without query) is a general error and stops the processing of the remaining keys.
  • Initialization failure: If the Worker fails to load or SQLite does not initialize (for example, because the files are not at the expected path or the CSP prevents compiling WebAssembly), all pending and later requests receive that error as a general error: the callback receives response.error, and the promise is rejected. If the Worker fails after it has started, the error is only shown in the console.

Example of per-key errors with a callback:

_sqlite_frontend({ 'nonexistent_column': true }).get(function(res) {
	// 1. General error in the response
	if (res.error) {
		console.error('General error:', res.error);
		return;
	}

	// 2. Error for the queried key
	if (res.get.nonexistent_column.error) {
		console.warn('Column error:', res.get.nonexistent_column.error);
		return;
	}

	console.log('Results:', res.get.nonexistent_column.result);
});

3. String methods (String)

They run raw SQL, select the active database or table, and export or close databases. The string cannot be empty: with an empty string, no request is sent, and the method returns undefined (the callback is not invoked and no promise is returned).

.sql(callback?, timeout?)

Runs a raw SQL query on the active database. The result (rows as objects) is in res.sql.result. If the string contains several statements, all of them run, but result only collects the rows of the first one that returns results. The string runs as is, without parameters: do not concatenate user input into it.

_sqlite_frontend('PRAGMA database_list;').sql(function(res) {
	console.log('Active databases:', res);
});

_sqlite_frontend("SELECT name FROM sqlite_master WHERE type='table'").sql(function(res) {
	console.log('Tables in the DB:', res);
});

.db(callback?, timeout?)

Selects the active database; subsequent operations are directed to it. When the library loads, the active database is _default_db, and it stays in use until another one is selected with .db() or one is opened with .open(). If the database does not exist, it is created (in OPFS if available; otherwise, in memory). Only the characters [a-zA-Z0-9_.] of the name are kept; if none remain, _default_db is used. The active table does not change: it is created in the new database if it does not exist. The response includes res.db.name and res.opfs (true if the database is in OPFS).

// Select 'my_database.db' as the active database
_sqlite_frontend('my_database.db').db();

.table(callback?, timeout?)

Selects the active table, on which the object methods operate (.column(), .row(), .get(), .set(), .del()). Until one is selected, _default_table is used. If the table does not exist in the active database, it is created with the auto-increment primary key _auto_id.

// Select 'users' as the active table for the following operations
_sqlite_frontend('users').table();

.save(callback?, timeout?)

Exports a database as a Blob of type application/x-sqlite3, available in res.save.data. It does not download anything by itself: if a download is needed, the page’s code handles it (see the example). The string is the name of the database to export; if none is open with that name, the active database is exported. In both cases, res.save.name contains that name (sanitized), which is useful as a file name.

_sqlite_frontend('backup.sqlite').save(function(res) {
	if (res.error) {
		console.error('Export error:', res.error);
		return;
	}
	var url = URL.createObjectURL(res.save.data);
	var a = document.createElement('a');
	a.href = url;
	a.download = res.save.name;
	document.body.appendChild(a);
	a.click();
	document.body.removeChild(a);
	// Revoke the URL later: doing it right after click() can cancel the download
	setTimeout(function() { URL.revokeObjectURL(url); }, 1000);
});

.close(callback?, timeout?)

Closes the database with the given name and frees its resources in the Web Worker. If none is open with that name, the response does not include res.close.name. Closing the active database does not change the selection: the next operation opens it again.

// 1. With async/await (inside an async function or a module)
try {
	var res = await _sqlite_frontend('my_database.db').close();
	console.log('Database closed:', res.close.name);
}
catch (error) {
	console.error('Error closing the DB:', error.message);
}

// 2. With a callback
_sqlite_frontend('my_database.db').close(function(res) {
	if (res.error) {
		console.error('Error:', res.error);
		return;
	}
	console.log('Database closed successfully:', res.close.name);
});

4. Object methods (Object)

They let you define columns and read or modify data in the active table without writing SQL (a query builder).

In .get(), .set(), and .del(), each key of the object is a column name (or several separated by commas, such as 'name, age'), and its value indicates which rows are affected (in .set(), also the new value). Each key is processed separately, and its result is in res[method][key].result. The examples in this section assume an active table with the columns date (INTEGER) and status (TEXT).

Note on numeric IDs: When the value that selects the rows is a number (or a numeric string), it is interpreted as the row’s _auto_id, the auto-generated primary key: the operation affects only the row with that ID. Values between 1 and Number.MAX_SAFE_INTEGER are accepted; outside that range, or with a non-numeric string, the key returns the Wrong ID error. The number 0 is not an ID: it counts as a falsy value.

.column(callback?, timeout?)

Adds a column to the active table: name is its name, and type is its SQLite type (default: TEXT). If the column already exists, it is not modified and no error is produced.

_sqlite_frontend({ name: 'date', type: 'INTEGER' }).column(function(res) {
	console.log('Column created or already exists:', res.column.name, res.column.type);
});

.row(callback?, timeout?)

Inserts a row into the active table. The keys are names of existing columns. The row receives an auto-incrementing _auto_id, available in res.row.id. With an empty object, nothing is inserted, and the response does not include res.row.

_sqlite_frontend({ date: Date.now() }).row(function(res) {
	console.log('ID assigned to the row:', res.row.id);
});

.get(callback?, timeout?)

Queries rows of the active table. The key is '*' (all columns) or one or more columns. The value can be:

  • true: all rows.
  • A number: the row with that _auto_id (see the note on numeric IDs at the start of this section).
  • An object with where (see “The where clause”), limit (maximum number of rows), and count (true to get the number of rows instead of the rows; with distinct: true, it counts distinct values).
  • A falsy value (false, 0, null): no rows (result is []).
  • An empty object ({}): the query is not run, and the key receives the error Empty criteria object; nothing was executed.

The result is an array of rows (objects) or, with count, a number.

// 1. Get all columns and rows
_sqlite_frontend({ '*': true }).get(function(res) {
	console.log('Rows:', res.get['*'].result);
});

// 2. Query filtered by _auto_id with where
_sqlite_frontend({
	'date': {
		where: { _auto_id: 1 }
	}
}).get(function(res) {
	console.log('Date obtained:', res.get.date.result);
});

// 3. Numeric ID shortcut (_auto_id = 1)
_sqlite_frontend({ '*': 1 }).get(function(res) {
	console.log('Row #1:', res.get['*'].result);
});

// 4. Query with operators and a limit
_sqlite_frontend({
	'date': {
		where: {
			date: { '>=': 1000000 },
			status: { 'IN': ['active', 'pending'] }
		},
		limit: 10
	}
}).get(function(res) {
	console.log('Filtered results:', res.get.date.result);
});

// 5. Count rows
_sqlite_frontend({ '*': { count: true, where: { status: 'active' } } }).get(function(res) {
	console.log('Active rows:', res.get['*'].result);
});

// 6. Rejects the promise with Error('SQLite request timeout.') if 2000 ms are exceeded
//    (inside an async function or a module)
try {
	// To set the timeout with promises, pass null or undefined as the first argument
	var data = await _sqlite_frontend({ '*': true }).get(null, 2000);
	console.log(data.get['*'].result);
} catch (err) {
	console.error('Query timed out:', err.message);
}

The where clause

It can be used in .get(), in .del(), and inside the query of .set(), as an object or as a string.

As an object: each key is a column, and the conditions of several keys are combined with AND. The values are passed as parameters (bind); they are not inserted into the SQL.

  • Simple value (number, string, or boolean): column = value. With null: column IS NULL.
  • Object { operator: value }: column operator value. Several operators on the same column are combined with AND; for example, { date: { '>=': 10, '<': 20 } } is a range.

Supported operators (case-insensitive: 'in' is equivalent to 'IN'):

  • Comparison: =, ==, !=, <>, >, <, <=, >=
  • Patterns: LIKE, NOT LIKE, GLOB, NOT GLOB
  • Sets: IN, NOT IN (with an array or a single value; with an empty array, IN selects no rows and NOT IN selects all of them)
  • Nulls and identity: IS, IS NOT (with null they generate IS NULL / IS NOT NULL), IS DISTINCT FROM, IS NOT DISTINCT FROM
  • Bits: &; the row is included if the result is not 0. For example, { permissions: { '&': 4 } } selects the rows in which the bit with value 4 is set.

Other operators (BETWEEN, OR, NOT, EXISTS…) cannot be expressed in object form: unknown ones are ignored, and several of those names produce an SQL error or, in the case of AND and OR, insert their value into the SQL without parameters, so do not use them. The keys AND, OR, and NOT at the top level of where are ignored, as are values that are neither simple values nor operator objects (for example, an array). For those cases, use where as a string.

Ignored conditions: in .get(), an ignored condition does not filter; if none remain, the query runs without WHERE and returns all rows. In .set() and .del(), in that case the operation does not run (see “Protection against criteria without conditions” in .set()).

As a string: the text is appended after WHERE as is (only leading and trailing spaces are trimmed), without parameters; do not include user input in it.

_sqlite_frontend({
	'*': { where: "date BETWEEN 1000 AND 2000 OR status = 'active'" }
}).get(function(res) {
	console.log(res.get['*'].result);
});

Compatibility note: count, distinct, and limit only apply in .get(). In .del() and in the query of .set(), count and limit leave an error on the corresponding key, and the operation does not run; distinct is ignored.

.set(callback?, timeout?)

Updates rows of the active table. The key is one or more columns ('*' is not allowed), and the value is an object with two properties: set, the new value, and query, which indicates which rows are updated: a row’s _auto_id (a number or a numeric string; see the note on numeric IDs at the start of this section) or an object with where (see “The where clause”). With query: true, all rows are updated, and with a falsy query (0, null, false), none are (result is []). If the key includes several columns, all of them receive the same value. The number of modified rows is in res.set[key].result.

// 1. Update the row with _auto_id = 1
_sqlite_frontend({
	'date': { set: 9999, query: 1 }
}).set(function(res) {
	console.log('Modified rows:', res.set.date.result);
});

// 2. Update the rows that meet a where condition
_sqlite_frontend({
	'status': { set: 'archived', query: { where: { date: { '<': 1000000 } } } }
}).set(function(res) {
	console.log('Modified rows:', res.set.status.result);
});

// 3. Update ALL rows (without query)
_sqlite_frontend({ 'status': 'active' }).set(function(res) {
	console.log('Modified rows:', res.set.status.result);
});

Global update warning: If query is omitted, either by passing the value directly ({ 'status': 'active' }) or by using { set: value }, the update runs without WHERE and applies the new value to all rows of the active table. A query with the value undefined (for example, an unassigned variable) counts as omitted.

Protection against criteria without conditions: in .set() (inside query) and in .del(), if a criteria object produces no WHERE condition (it does not include where, where is empty—{} or ''—or all its conditions are ignored), the operation does not run, and res.set[key].error (or res.del[key].error) reports it. This way, a badly written filter does not affect the whole table. An empty criteria object ({}) does not run either and leaves the error Empty criteria object; nothing was executed. To affect all rows, use true in .del(), or .set() without query (or with query: true).

.del(callback?, timeout?)

Deletes entire rows from the active table. The key is a column name ('*' is not allowed) that only identifies the result in res.del[key]: it does not limit what is deleted. The value indicates which rows are deleted: a number (_auto_id; see the note on numeric IDs at the start of this section), an object with where, or true (all of them). A falsy value deletes nothing (result is []). The number of deleted rows is in res.del[key].result.

// 1. Delete the row with _auto_id = 1
_sqlite_frontend({ 'date': 1 }).del(function(res) {
	console.log('Deleted rows:', res.del.date.result);
});

// 2. Delete the rows that meet a where condition
_sqlite_frontend({
	'date': { where: { date: 0 } }
}).del(function(res) {
	console.log('Deleted rows:', res.del.date.result);
});

Mass deletion warning: With the value true (for example, { date: true }), the deletion runs without WHERE and removes all rows from the active table.

.open(callback?, timeout?)

Loads a database from binary data (ArrayBuffer or a view such as Uint8Array or another TypedArray). name is the name it is stored under (sanitized as in .db(); the response returns it in res.open.name). The loaded database becomes the active one and, if OPFS is available, it is stored persistently in OPFS (res.opfs indicates whether this is the case). If a database with that name already exists, it is closed and replaced by the new one.

If data is neither an ArrayBuffer nor a view, or its content is not a valid SQLite database, the load fails without closing any database already open with that name (if what fails is the copy to OPFS, that database has already been closed), and the active database only changes if the load succeeds. Any failure, including while copying to OPFS, is a general error (res.error; with promises, the promise is rejected). Since the Worker handles requests one at a time, operations issued after .open() wait for it to finish, including the copy to OPFS.

// Example with a file input: <input type="file" id="db_file">
// (inside an async function or a module)
var file = document.getElementById('db_file').files[0];
var buffer = await file.arrayBuffer();

// 1. With async/await
try {
	var res = await _sqlite_frontend({
		name: file.name,
		data: buffer
	}).open();

	console.log('Database loaded:', res.open.name);
}
catch (error) {
	console.error('Error opening the DB:', error.message);
}

// 2. With a callback
_sqlite_frontend({
	name: 'my_backup.sqlite',
	data: buffer
}).open(function(res) {
	if (res.error) {
		console.error('Error opening:', res.error);
		return;
	}
	console.log('Database ready to use:', res.open.name);
});

5. Full example

Schema definition, insertion, query, update, and deletion:

document.addEventListener('DOMContentLoaded', async function () {
	// 1. Create a column in the schema
	await _sqlite_frontend({ name: 'date', type: 'INTEGER' }).column();

	// 2. Insert a row
	var insertion = await _sqlite_frontend({ date: Date.now() }).row();
	var newId = insertion.row.id;
	console.log('Row inserted with _auto_id:', newId);

	// 3. Query all rows
	var data = await _sqlite_frontend({ '*': true }).get();
	console.log('Read result:', data.get['*'].result);

	// 4. Update the newly inserted row
	await _sqlite_frontend({
		'date': { set: 9999, query: newId }
	}).set();

	// 5. Delete the row by its _auto_id
	await _sqlite_frontend({ 'date': newId }).del();
	console.log('Row deleted.');
});

6. Late responses (unhandledResponse)

If an operation with timeout takes longer than the given time, the request is removed from the internal queue: with promises, the promise is rejected; with a callback, the callback is not invoked.

The Web Worker, however, finishes the operation and sends its result to the main thread (unless the time expired before SQLite finished loading: in that case, the operation is never sent). To receive those responses, define the global handler _sqlite_frontend.unhandledResponse, which is invoked with each response that no longer has a pending request.

Use case: Logging or recovering the result of operations whose timeout expired on the page but that SQLite completed.

Configuration example:

// Global handler for responses that arrive after the timeout
_sqlite_frontend.unhandledResponse = function (response) {
	console.warn('Response received after the timeout (ID ' + response.id + '):', response);

	// If the operation was an update, its result can be checked
	if (response.set) {
		console.log('The update was completed in the background.');
	}
};

// Query with a 1 ms timeout
_sqlite_frontend({ '*': true }).get(null, 1).catch(function(error) {
	console.error('Timeout on the page:', error.message);
	// If the Worker responds later, 'unhandledResponse' receives the result.
});

7. Technical details

Execution in a Web Worker: Queries and disk access run in a background thread, without blocking the interface. The Worker processes requests one at a time, in the order they arrive.

OPFS or memory: If the browser allows using the origin private file system (OPFS), databases are stored there persistently. If not (for example, without the headers in section 8), they are created in memory and lost when the page is closed. The res.opfs property of each response indicates which mode is in use.

Pre-initialization queue: Operations issued before SQLite finishes loading are stored and sent, in the order they were issued, once it is ready.

Name and parameter sanitization: For database names, only the characters [a-zA-Z0-9_.] are kept, and for table and column names, [a-zA-Z0-9_]; the rest are removed. The values of .row(), .set(), and object-form where are passed as parameters (bind), except those of the unsupported operators mentioned in “The where clause”. .sql() and string-form where run without parameters.

8. Server HTTP headers

To store data in OPFS (Origin Private File System), SQLite WASM needs SharedArrayBuffer, which the browser only enables when the page is cross-origin isolated. Without these headers, the library works in memory (res.opfs === false).

Headers required for OPFS:

  • Cross-Origin-Opener-Policy: same-origin (COOP).
  • Cross-Origin-Embedder-Policy: require-corp (COEP). Note: With this header, the browser blocks every cross-origin resource (CDN scripts, images, fonts, iframes…) that neither sends Cross-Origin-Resource-Policy: cross-origin nor is loaded through CORS (the crossorigin attribute and CORS headers on the server that hosts the resource).

If the site uses a Content Security Policy (CSP):

  • Content-Security-Policy: script-src … 'wasm-unsafe-eval' (allows compiling the WebAssembly module; without it, SQLite does not initialize).

Optional:

  • Cross-Origin-Resource-Policy: same-origin (CORP). Additional protection that prevents other origins from embedding the site’s resources; it is not a requirement for OPFS.

Middleware example in Node.js (Express or your own server):

module.exports = function customMiddleware (req, res, next) {
	// Cross-origin isolation, required for OPFS
	res.setHeader('Cross-Origin-Opener-Policy', 'same-origin');
	res.setHeader('Cross-Origin-Embedder-Policy', 'require-corp');

	// Allows compiling WebAssembly. Adapt this value to the site’s existing CSP:
	// add 'wasm-unsafe-eval' to its script-src instead of replacing the whole policy.
	res.setHeader('Content-Security-Policy', "script-src 'self' 'wasm-unsafe-eval'");

	// Optional: additional protection, not required for OPFS
	res.setHeader('Cross-Origin-Resource-Policy', 'same-origin');

	next();
};
