SQLite Frontend

Descripción

Base de datos SQLite compilada a WebAssembly (WASM) para el navegador. Las operaciones se ejecutan en un hilo secundario (Web Worker), de modo que no bloquean la interfaz. Los datos se guardan de forma persistente en el sistema de archivos privado del origen (OPFS) cuando el navegador y las cabeceras del servidor lo permiten; si no, en memoria. Ofrece SQL directo sobre cadenas y métodos encadenables sobre objetos (query builder), con callbacks o promesas.

Librería: estructura.sqlite.frontend.js

Compatibilidad: ES6+ / WebAssembly / Web Workers / OPFS

Estado: RC2

Licencia: AGPL v3

Archivos necesarios (autoalojados): estructura.sqlite.frontend.js, estructura.sqlite.frontend.wasm.worker.js y el directorio _dependencies/_sqlite/ (SQLite WASM v3.53.0-build1, oficial). El Worker se crea con la ruta relativa ./estructura.sqlite.frontend.wasm.worker.js, que el navegador resuelve respecto a la página (no respecto al script), y el Worker importa ./_dependencies/_sqlite/index.mjs respecto a sí mismo. Por eso el Worker y el directorio _dependencies/_sqlite/ deben estar en el mismo directorio que la página HTML que usa la librería (lo más sencillo es colocar ahí también estructura.sqlite.frontend.js). Un Worker solo puede cargarse desde el mismo origen que la página, así que estos archivos no pueden servirse desde un CDN.

Demo en vivo

Pulse «Ejecutar demo» para crear una columna, insertar, consultar, actualizar y borrar filas en la base de datos activa; los resultados se muestran en la consola del navegador y, al final, se descarga una copia de la base de datos (test.db.sqlite). También puede seleccionar un archivo .sqlite propio (mínimo 20 KB): la demo lo abre con .open() y después ejecuta las mismas operaciones sobre él.

Documentación

Inicio rápido

El siguiente ejemplo crea una tabla con una columna, inserta una fila y la lee (dentro de una función async):

async function iniciar() {
	await _sqlite_frontend('notas').table();
	await _sqlite_frontend({ name: 'texto', type: 'TEXT' }).column();
	await _sqlite_frontend({ texto: 'Hola' }).row();

	var res = await _sqlite_frontend({ '*': true }).get();
	console.log(res.get['*'].result); // [{ _auto_id: …, texto: 'Hola' }]
}

iniciar();

1. Modelo de ejecución

La librería expone la función global _sqlite_frontend. Todas las operaciones se envían a un Web Worker (estructura.sqlite.frontend.wasm.worker.js) que ejecuta SQLite.

Callbacks o promesas:

Cada método admite un callback como primer argumento opcional y un tiempo límite en milisegundos (timeout) como segundo. Si se omite el callback, el método devuelve una promesa (Promise), utilizable con async/await; si se pasa un callback, devuelve undefined.

// 1. Con promesas (dentro de una función async o de un módulo)
try {
	var resultado = await _sqlite_frontend('SELECT * FROM usuarios').sql();
	console.log('Datos:', resultado.sql.result);
} catch (error) {
	console.error('Error SQL:', error.message);
}

// 2. Con callback
_sqlite_frontend('SELECT * FROM usuarios').sql(function(respuesta) {
	if (respuesta.error) {
		console.error('Error:', respuesta.error);
		return;
	}
	console.log('Resultado:', respuesta.sql.result);
});

2. Errores

Los errores de una operación llegan en la respuesta del Worker:

  • Con promesas: Si la respuesta contiene un error general (respuesta.error), la promesa se rechaza con un Error cuyo mensaje es ese texto; la respuesta completa está en error.response. Los errores de una clave concreta en .get(), .set() o .del() no rechazan la promesa: se resuelve y el error queda en respuesta[método][clave].error.
  • Con callbacks: El callback recibe siempre el objeto de respuesta. Si hubo un fallo general, respuesta.error contiene el mensaje.
  • Errores por clave: Cuando una llamada a .get(), .set() o .del() incluye varias claves, el fallo de una no impide que se procesen las demás; queda aislado en respuesta[método][clave].error. Excepción: un fallo en una actualización global de .set() (sin query) es un error general y detiene el procesamiento de las claves restantes.
  • Fallo de inicialización: Si el Worker no llega a cargarse o SQLite no se inicializa (por ejemplo, porque los archivos no están en la ruta esperada o la CSP impide compilar WebAssembly), todas las peticiones pendientes y las posteriores reciben ese error como error general: el callback recibe respuesta.error y la promesa se rechaza. Si el Worker falla después de haber arrancado, el error solo se muestra en la consola.

Ejemplo de errores por clave con callback:

_sqlite_frontend({ 'columna_inexistente': true }).get(function(res) {
	// 1. Error general de la respuesta
	if (res.error) {
		console.error('Error general:', res.error);
		return;
	}

	// 2. Error de la clave consultada
	if (res.get.columna_inexistente.error) {
		console.warn('Error en la columna:', res.get.columna_inexistente.error);
		return;
	}

	console.log('Resultados:', res.get.columna_inexistente.result);
});

3. Métodos para cadenas (String)

Ejecutan SQL directo, seleccionan la base de datos o la tabla activa, y exportan o cierran bases de datos. La cadena no puede estar vacía: con una cadena vacía no se envía ninguna petición y el método devuelve undefined (no se invoca el callback ni se devuelve promesa).

.sql(callback?, timeout?)

Ejecuta una consulta SQL directa en la base de datos activa. El resultado (filas como objetos) está en res.sql.result. Si la cadena contiene varias sentencias, se ejecutan todas, pero result solo recoge las filas de la primera que devuelve resultados. La cadena se ejecuta tal cual, sin parámetros: no concatene en ella datos introducidos por el usuario.

_sqlite_frontend('PRAGMA database_list;').sql(function(res) {
	console.log('Bases de datos activas:', res);
});

_sqlite_frontend("SELECT name FROM sqlite_master WHERE type='table'").sql(function(res) {
	console.log('Tablas en la BD:', res);
});

.db(callback?, timeout?)

Selecciona la base de datos activa; las operaciones posteriores se dirigen a ella. Al cargar la librería, la base de datos activa es _default_db, y se sigue usando hasta que se seleccione otra con .db() o se abra una con .open(). Si la base de datos no existe, se crea (en OPFS si está disponible; si no, en memoria). Del nombre solo se conservan los caracteres [a-zA-Z0-9_.]; si no queda ninguno, se usa _default_db. La tabla activa no cambia: se crea en la nueva base de datos si no existe. La respuesta incluye res.db.name y res.opfs (true si la base de datos está en OPFS).

// Seleccionar 'mi_base_datos.db' como base de datos activa
_sqlite_frontend('mi_base_datos.db').db();

.table(callback?, timeout?)

Selecciona la tabla activa, sobre la que operan los métodos para objetos (.column(), .row(), .get(), .set(), .del()). Mientras no se seleccione ninguna, se usa _default_table. Si la tabla no existe en la base de datos activa, se crea con la clave primaria autoincremental _auto_id.

// Seleccionar 'usuarios' como tabla activa para las operaciones siguientes
_sqlite_frontend('usuarios').table();

.save(callback?, timeout?)

Exporta una base de datos como un Blob de tipo application/x-sqlite3, disponible en res.save.data. No descarga nada por sí mismo: la descarga, si se desea, la hace el código de la página (ver ejemplo). La cadena es el nombre de la base de datos que se exporta; si no hay ninguna abierta con ese nombre, se exporta la base de datos activa. En ambos casos, res.save.name contiene ese nombre (saneado), útil como nombre de archivo.

_sqlite_frontend('respaldo.sqlite').save(function(res) {
	if (res.error) {
		console.error('Error al exportar:', res.error);
		return;
	}
	var url = URL.createObjectURL(res.save.data);
	var a = document.createElement('a');
	a.href = url;
	a.download = res.save.name;
	document.body.appendChild(a);
	a.click();
	document.body.removeChild(a);
	// Revocar la URL más tarde: hacerlo justo tras click() puede cancelar la descarga
	setTimeout(function() { URL.revokeObjectURL(url); }, 1000);
});

.close(callback?, timeout?)

Cierra la base de datos con el nombre indicado y libera sus recursos en el Web Worker. Si no hay ninguna abierta con ese nombre, la respuesta no incluye res.close.name. Cerrar la base de datos activa no cambia la selección: la siguiente operación la vuelve a abrir.

// 1. Con async/await (dentro de una función async o de un módulo)
try {
	var res = await _sqlite_frontend('mi_base_datos.db').close();
	console.log('Base de datos cerrada:', res.close.name);
}
catch (error) {
	console.error('Error al cerrar BD:', error.message);
}

// 2. Con callback
_sqlite_frontend('mi_base_datos.db').close(function(res) {
	if (res.error) {
		console.error('Error:', res.error);
		return;
	}
	console.log('Base de datos cerrada correctamente:', res.close.name);
});

4. Métodos para objetos (Object)

Permiten definir columnas y leer o modificar datos de la tabla activa sin escribir SQL (query builder).

En .get(), .set() y .del(), cada clave del objeto es un nombre de columna (o varios separados por comas, como 'nombre, edad') y su valor indica qué filas se ven afectadas (en .set(), también el nuevo valor). Cada clave se procesa por separado y su resultado está en res[método][clave].result. Los ejemplos de esta sección suponen una tabla activa con las columnas fecha (INTEGER) y estado (TEXT).

Nota sobre IDs numéricos: Cuando el valor que selecciona las filas es un número (o una cadena numérica), se interpreta como el _auto_id de la fila, la clave primaria autogenerada: la operación afecta solo a la fila con ese ID. Se aceptan valores entre 1 y Number.MAX_SAFE_INTEGER; fuera de ese rango, o con una cadena no numérica, la clave devuelve el error Wrong ID. El número 0 no es un ID: cuenta como valor falso.

.column(callback?, timeout?)

Añade una columna a la tabla activa: name es su nombre y type, su tipo SQLite (por defecto, TEXT). Si la columna ya existe, no se modifica ni se produce un error.

_sqlite_frontend({ name: 'fecha', type: 'INTEGER' }).column(function(res) {
	console.log('Columna creada o ya existente:', res.column.name, res.column.type);
});

.row(callback?, timeout?)

Inserta una fila en la tabla activa. Las claves son nombres de columnas existentes. La fila recibe un _auto_id autoincremental, disponible en res.row.id. Con un objeto vacío no se inserta nada y la respuesta no incluye res.row.

_sqlite_frontend({ fecha: Date.now() }).row(function(res) {
	console.log('ID asignado a la fila:', res.row.id);
});

.get(callback?, timeout?)

Consulta filas de la tabla activa. La clave es '*' (todas las columnas) o una o varias columnas. El valor puede ser:

  • true: todas las filas.
  • Un número: la fila con ese _auto_id (ver la nota sobre IDs numéricos al inicio de esta sección).
  • Un objeto con where (ver «Cláusula where»), limit (número máximo de filas) y count (true para obtener el número de filas en lugar de las filas; con distinct: true, cuenta valores distintos).
  • Un valor falso (false, 0, null): ninguna fila (result es []).
  • Un objeto vacío ({}): no se ejecuta la consulta y la clave recibe el error Empty criteria object; nothing was executed.

El resultado es un array de filas (objetos) o, con count, un número.

// 1. Obtener todas las columnas y filas
_sqlite_frontend({ '*': true }).get(function(res) {
	console.log('Filas:', res.get['*'].result);
});

// 2. Consulta filtrada por _auto_id con where
_sqlite_frontend({
	'fecha': {
		where: { _auto_id: 1 }
	}
}).get(function(res) {
	console.log('Fecha obtenida:', res.get.fecha.result);
});

// 3. Atajo por ID numérico (_auto_id = 1)
_sqlite_frontend({ '*': 1 }).get(function(res) {
	console.log('Fila #1:', res.get['*'].result);
});

// 4. Consulta con operadores y límite
_sqlite_frontend({
	'fecha': {
		where: {
			fecha: { '>=': 1000000 },
			estado: { 'IN': ['activo', 'pendiente'] }
		},
		limit: 10
	}
}).get(function(res) {
	console.log('Resultados filtrados:', res.get.fecha.result);
});

// 5. Contar filas
_sqlite_frontend({ '*': { count: true, where: { estado: 'activo' } } }).get(function(res) {
	console.log('Filas activas:', res.get['*'].result);
});

// 6. Rechaza la promesa con Error('SQLite request timeout.') si se superan los 2000 ms
//    (dentro de una función async o de un módulo)
try {
	// Para indicar el timeout con promesas, pase null o undefined como primer argumento
	var datos = await _sqlite_frontend({ '*': true }).get(null, 2000);
	console.log(datos.get['*'].result);
} catch (err) {
	console.error('Consulta cancelada por tiempo:', err.message);
}

Cláusula where

Se puede usar en .get(), en .del() y dentro del query de .set(), como objeto o como cadena.

Como objeto: cada clave es una columna, y las condiciones de varias claves se combinan con AND. Los valores se pasan como parámetros (bind), no se insertan en el SQL.

  • Valor simple (número, cadena o booleano): columna = valor. Con null: columna IS NULL.
  • Objeto { operador: valor }: columna operador valor. Varios operadores en la misma columna se combinan con AND; por ejemplo, { fecha: { '>=': 10, '<': 20 } } es un rango.

Operadores admitidos (sin distinguir mayúsculas: 'in' equivale a 'IN'):

  • Comparación: =, ==, !=, <>, >, <, <=, >=
  • Patrones: LIKE, NOT LIKE, GLOB, NOT GLOB
  • Conjuntos: IN, NOT IN (con un array o un valor único; con un array vacío, IN no selecciona ninguna fila y NOT IN, todas)
  • Nulos e identidad: IS, IS NOT (con null generan IS NULL / IS NOT NULL), IS DISTINCT FROM, IS NOT DISTINCT FROM
  • Bits: &; la fila se incluye si el resultado es distinto de 0. Por ejemplo, { permisos: { '&': 4 } } selecciona las filas cuyo bit de valor 4 está activo.

Otros operadores (BETWEEN, OR, NOT, EXISTS…) no se pueden expresar en forma de objeto: los desconocidos se ignoran, y varios de esos nombres producen un error de SQL o, como AND y OR, insertan su valor en el SQL sin parámetros, así que no los use. Las claves AND, OR y NOT en el primer nivel de where se ignoran, igual que los valores que no son simples ni objetos de operadores (por ejemplo, un array). Para esos casos, use where como cadena.

Condiciones ignoradas: en .get(), una condición ignorada no filtra; si no queda ninguna, la consulta se ejecuta sin WHERE y devuelve todas las filas. En .set() y .del(), en ese caso la operación no se ejecuta (ver «Protección ante criterios sin condiciones», en .set()).

Como cadena: el texto se añade tras WHERE tal cual (solo se recortan los espacios de los extremos), sin parámetros; no incluya en él datos introducidos por el usuario.

_sqlite_frontend({
	'*': { where: "fecha BETWEEN 1000 AND 2000 OR estado = 'activo'" }
}).get(function(res) {
	console.log(res.get['*'].result);
});

Nota de compatibilidad: count, distinct y limit solo se aplican en .get(). En .del() y en el query de .set(), count y limit dejan un error en la clave correspondiente y la operación no se ejecuta; distinct se ignora.

.set(callback?, timeout?)

Actualiza filas de la tabla activa. La clave es una o varias columnas (no se admite '*') y el valor es un objeto con dos propiedades: set, el nuevo valor, y query, que indica qué filas se actualizan: el _auto_id de una fila (un número o una cadena numérica; ver la nota sobre IDs numéricos al inicio de esta sección) o un objeto con where (ver «Cláusula where»). Con query: true se actualizan todas las filas, y con un query falso (0, null, false), ninguna (result es []). Si la clave incluye varias columnas, todas reciben el mismo valor. El número de filas modificadas está en res.set[clave].result.

// 1. Actualizar la fila con _auto_id = 1
_sqlite_frontend({
	'fecha': { set: 9999, query: 1 }
}).set(function(res) {
	console.log('Filas modificadas:', res.set.fecha.result);
});

// 2. Actualizar las filas que cumplen una condición where
_sqlite_frontend({
	'estado': { set: 'archivado', query: { where: { fecha: { '<': 1000000 } } } }
}).set(function(res) {
	console.log('Filas modificadas:', res.set.estado.result);
});

// 3. Actualizar TODAS las filas (sin query)
_sqlite_frontend({ 'estado': 'activo' }).set(function(res) {
	console.log('Filas modificadas:', res.set.estado.result);
});

Advertencia de actualización global: Si no se indica query, ya sea con el valor directo ({ 'estado': 'activo' }) o con { set: valor }, la actualización se ejecuta sin WHERE y aplica el nuevo valor a todas las filas de la tabla activa. Un query con valor undefined (por ejemplo, una variable sin asignar) cuenta como no indicado.

Protección ante criterios sin condiciones: en .set() (dentro de query) y en .del(), si un objeto de criterios no produce ninguna condición WHERE (no incluye where, where está vacío —{} o ''— o todas sus condiciones se ignoran), la operación no se ejecuta y res.set[clave].error (o res.del[clave].error) lo indica. Así un filtro mal escrito no afecta a toda la tabla. Un objeto de criterios vacío ({}) tampoco se ejecuta y deja el error Empty criteria object; nothing was executed. Para afectar a todas las filas, use true en .del(), o .set() sin query (o con query: true).

.del(callback?, timeout?)

Borra filas completas de la tabla activa. La clave es un nombre de columna (no se admite '*') que solo identifica el resultado en res.del[clave]: no limita lo que se borra. El valor indica qué filas se borran: un número (_auto_id; ver la nota sobre IDs numéricos al inicio de esta sección), un objeto con where, o true (todas). Un valor falso no borra nada (result es []). El número de filas borradas está en res.del[clave].result.

// 1. Borrar la fila con _auto_id = 1
_sqlite_frontend({ 'fecha': 1 }).del(function(res) {
	console.log('Filas borradas:', res.del.fecha.result);
});

// 2. Borrar las filas que cumplen una condición where
_sqlite_frontend({
	'fecha': { where: { fecha: 0 } }
}).del(function(res) {
	console.log('Filas borradas:', res.del.fecha.result);
});

Advertencia de borrado masivo: Con el valor true (por ejemplo, { fecha: true }), el borrado se ejecuta sin WHERE y elimina todas las filas de la tabla activa.

.open(callback?, timeout?)

Carga una base de datos a partir de datos binarios (ArrayBuffer o una vista como Uint8Array u otro TypedArray). name es el nombre con el que se guarda (saneado como en .db(); la respuesta lo devuelve en res.open.name). La base de datos cargada pasa a ser la activa y, si OPFS está disponible, se guarda de forma persistente en OPFS (res.opfs indica si es así). Si ya existe una base de datos con ese nombre, se cierra y se sustituye por la nueva.

Si data no es un ArrayBuffer ni una vista, o su contenido no es una base de datos SQLite válida, la carga falla sin cerrar la base de datos que ya estuviera abierta con ese nombre, y la activa solo cambia si la carga termina bien. Cualquier fallo, también al copiar a OPFS, es un error general (res.error; con promesas, la promesa se rechaza). Como el Worker atiende las peticiones de una en una, las operaciones lanzadas después de .open() esperan a que termine, copia a OPFS incluida.

// Ejemplo con un input de tipo archivo: <input type="file" id="archivo_db">
// (dentro de una función async o de un módulo)
var file = document.getElementById('archivo_db').files[0];
var buffer = await file.arrayBuffer();

// 1. Con async/await
try {
	var res = await _sqlite_frontend({
		name: file.name,
		data: buffer
	}).open();

	console.log('Base de datos cargada:', res.open.name);
}
catch (error) {
	console.error('Error al abrir la BD:', error.message);
}

// 2. Con callback
_sqlite_frontend({
	name: 'mi_respaldo.sqlite',
	data: buffer
}).open(function(res) {
	if (res.error) {
		console.error('Error al abrir:', res.error);
		return;
	}
	console.log('Base de datos lista para operar:', res.open.name);
});

5. Ejemplo completo

Definición de esquema, inserción, consulta, actualización y borrado:

document.addEventListener('DOMContentLoaded', async function () {
	// 1. Crear columna en el esquema
	await _sqlite_frontend({ name: 'fecha', type: 'INTEGER' }).column();

	// 2. Insertar una fila
	var insercion = await _sqlite_frontend({ fecha: Date.now() }).row();
	var nuevoId = insercion.row.id;
	console.log('Fila insertada con _auto_id:', nuevoId);

	// 3. Consultar todas las filas
	var datos = await _sqlite_frontend({ '*': true }).get();
	console.log('Resultado de lectura:', datos.get['*'].result);

	// 4. Actualizar la fila recién insertada
	await _sqlite_frontend({
		'fecha': { set: 9999, query: nuevoId }
	}).set();

	// 5. Borrar la fila por su _auto_id
	await _sqlite_frontend({ 'fecha': nuevoId }).del();
	console.log('Fila borrada.');
});

6. Respuestas tardías (unhandledResponse)

Si una operación con timeout tarda más del tiempo indicado, la petición se elimina de la cola interna: con promesas, la promesa se rechaza; con callback, el callback no se invoca.

El Web Worker, sin embargo, termina la operación y envía su resultado al hilo principal (salvo si el tiempo expiró antes de que SQLite terminara de cargarse: en ese caso la operación no llega a enviarse). Para recibir esas respuestas, defina el manejador global _sqlite_frontend.unhandledResponse, que se invoca con cada respuesta que ya no tiene una petición pendiente.

Caso de uso: Registrar o recuperar el resultado de operaciones cuyo tiempo límite expiró en la página, pero que SQLite completó.

Ejemplo de configuración:

// Manejador global para respuestas que llegan tras el timeout
_sqlite_frontend.unhandledResponse = function (respuesta) {
	console.warn('Respuesta recibida tras el timeout (ID ' + respuesta.id + '):', respuesta);

	// Si la operación era una actualización, se puede comprobar su resultado
	if (respuesta.set) {
		console.log('La actualización se completó en segundo plano.');
	}
};

// Consulta con un timeout de 1 ms
_sqlite_frontend({ '*': true }).get(null, 1).catch(function(error) {
	console.error('Timeout en la página:', error.message);
	// Si el Worker responde después, 'unhandledResponse' recibe el resultado.
});

7. Características técnicas

Ejecución en Web Worker: Las consultas y el acceso a disco se ejecutan en un hilo secundario, sin bloquear la interfaz. El Worker procesa las peticiones de una en una, en el orden en que llegan.

OPFS o memoria: Si el navegador permite usar el sistema de archivos privado del origen (OPFS), las bases de datos se guardan en él de forma persistente. Si no (por ejemplo, sin las cabeceras de la sección 8), se crean en memoria y se pierden al cerrar la página. La propiedad res.opfs de cada respuesta indica qué modo se usa.

Cola previa a la inicialización: Las operaciones emitidas antes de que SQLite termine de cargarse se guardan y se envían, en el orden en que se emitieron, cuando está listo.

Saneamiento de nombres y parámetros: De los nombres de bases de datos solo se conservan los caracteres [a-zA-Z0-9_.], y de los de tablas y columnas, [a-zA-Z0-9_]; el resto se elimina. Los valores de .row(), .set() y de where en forma de objeto se pasan como parámetros (bind), salvo los de los operadores no admitidos que se citan en «Cláusula where». .sql() y where en forma de cadena se ejecutan sin parámetros.

8. Cabeceras HTTP del servidor

Para guardar datos en OPFS (Origin Private File System), SQLite WASM necesita SharedArrayBuffer, que el navegador solo habilita si la página está aislada por origen (cross-origin isolation). Sin estas cabeceras, la librería funciona en memoria (res.opfs === false).

Cabeceras necesarias para OPFS:

  • Cross-Origin-Opener-Policy: same-origin (COOP).
  • Cross-Origin-Embedder-Policy: require-corp (COEP). Nota: Con esta cabecera, el navegador bloquea todo recurso de otro origen (scripts de CDN, imágenes, fuentes, iframes…) que no envíe Cross-Origin-Resource-Policy: cross-origin o que no se cargue mediante CORS (atributo crossorigin y cabeceras CORS en el servidor de origen).

Si el sitio usa una política de seguridad de contenido (CSP):

  • Content-Security-Policy: script-src … 'wasm-unsafe-eval' (permite compilar el módulo WebAssembly; sin ella, SQLite no se inicializa).

Opcional:

  • Cross-Origin-Resource-Policy: same-origin (CORP). Protección adicional que impide que otros orígenes incrusten los recursos del sitio; no es un requisito de OPFS.

Ejemplo de middleware en Node.js (Express o servidor propio):

module.exports = function customMiddleware (req, res, next) {
	// Aislamiento de origen, necesario para OPFS
	res.setHeader('Cross-Origin-Opener-Policy', 'same-origin');
	res.setHeader('Cross-Origin-Embedder-Policy', 'require-corp');

	// Permite compilar WebAssembly. Adapte este valor a la CSP existente del sitio:
	// añada 'wasm-unsafe-eval' a su script-src en lugar de sustituir la política completa.
	res.setHeader('Content-Security-Policy', "script-src 'self' 'wasm-unsafe-eval'");

	// Opcional: protección adicional, no necesaria para OPFS
	res.setHeader('Cross-Origin-Resource-Policy', 'same-origin');

	next();
};
